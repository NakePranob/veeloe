## Context

`controller-foundation` วางแอป ตัวกั้นใน `src/app` และระบบข้อความไว้แล้ว ส่วน `packages/protocol` มี `generateSecretKey`, `createSigner` และ `verify` ที่ใช้ @noble อยู่แล้ว

## Goals / Non-Goals

**Goals:**
- กุญแจที่ `machine-pairing` เอาไปเซ็นได้เลย โดยไม่ต้องกลับมาแก้กติกาการล็อก

**Non-Goals:**
- การต่อ Hub และการเซ็นซองจริงอยู่ใน `machine-pairing`
- คำเตือนให้ Link เครื่องที่สองอยู่ใน `linking-and-revocation`
- PIN ของแอป เพิ่มทีหลังได้โดยไม่แก้ Protocol และไม่ต้องทำ Pairing ใหม่ เพราะสร้างสำเนาที่สองได้หลังปลดล็อกด้วย biometric

## Decisions

### บนมือถือใช้ biometric อย่างเดียว

`requireAuthentication` ของ `expo-secure-store` SDK 58 บน iOS สร้าง access control ด้วย `.biometryCurrentSet` อย่างเดียว ซึ่งตรงกับข้อความใน ADR 0012 เรื่องกุญแจใช้ไม่ได้เมื่อ biometric เปลี่ยน แต่ขัดกับประโยคที่ว่ารหัสเครื่องผ่านได้ เราคง `requireAuthentication` ไว้ เพราะ OS เป็นคนบังคับด่านนี้ ไม่ใช่ `if` ในแอป แล้วแก้ ADR 0012 กับ `CONTEXT.md` ใน commit เดียวกันกับโค้ด เช็กล่วงหน้าด้วย `canUseBiometricAuthentication()`

ทางเลือกที่ตัดออก:
- **ด่านในแอปด้วย `expo-local-authentication` และเก็บกุญแจแบบ `WHEN_PASSCODE_SET_THIS_DEVICE_ONLY`**: รหัสเครื่องผ่านได้ และเปลี่ยน biometric แล้วกุญแจไม่หาย แต่ด่านเหลือแค่โค้ดในแอป เครื่องที่ถูกเจาะจึงข้ามได้ง่ายกว่า
- **PIN 6 หลักของแอปตั้งแต่ตอนนี้**: แก้เรื่องเครื่องที่ไม่มี biometric และกุญแจหาย แต่ต้องมีสำเนาที่สองที่ป้องกันด้วยรหัสเพียง 1 ล้านแบบ พร้อม KDF, ตัวนับครั้งที่ผิด และหน้าตั้งกับลืม PIN และยังขัดกับเหตุผลเดิมใน ADR 0012 เจ้าของเลือกเลื่อนไปก่อน
- **native module ที่ใช้ `.userPresence`**: ได้ทั้ง OS บังคับและรหัสเครื่อง แต่ต้องดูแล native code เองทั้งที่ ADR 0012 เลือก @noble และ Expo เพื่อเลี่ยงเรื่องนี้

### แยกกติกาการล็อกออกจากการเก็บกุญแจ

`shared/keystore` มีสองส่วน:
- **vault:** แยกตาม platform (`vault.ts`, `vault.web.ts`) ทำหน้าที่บอกว่าเครื่องรองรับไหม สร้าง และอ่านส่วนลับ การอ่านทุกครั้งคือการยืนยันตัวหนึ่งครั้ง
- **session:** โค้ดล้วนที่รับ vault และ clock ถือสถานะ `none`, `lost`, `locked`, `unlocked` และเวลาที่ใช้ล่าสุด

กติกา 5 นาทีจึงทดสอบด้วย clock ปลอมได้ และการกระทำสำคัญคือการอ่าน vault อีกครั้งโดยไม่ไปแตะกุญแจที่ถืออยู่ ไม่มีระบบแยกอีกชุด

การเทียบเวลาทำตอนมีการแตะและตอนกลับจากพื้นหลัง เพราะ timer ไม่เดินเมื่อแอปอยู่พื้นหลัง ส่วน timer ระหว่างอยู่หน้าจอมีไว้ล้างกุญแจตรงเวลา การแตะจับที่ root ด้วย `onTouchStartCapture` และบนเว็บเพิ่ม `keydown` ด้วย

### บนมือถือมีสองรายการใน Keychain

- **ส่วนลับ:** ตั้ง `requireAuthentication` กับ `WHEN_UNLOCKED_THIS_DEVICE_ONLY` และใช้ `keychainService` ของตัวเอง เพราะเอกสารบอกว่ารายการแบบนี้ใช้ service ร่วมกับรายการที่ไม่ต้องยืนยันตัวไม่ได้
- **กุญแจสาธารณะ:** ไม่ต้องยืนยันตัว ใช้บอกว่าเครื่องเคยมีกุญแจ

เมื่อ biometric เปลี่ยน `getItemAsync` ของส่วนลับคืน `null` ถ้าไม่มีรายการที่สอง แอปจะแยกไม่ออกระหว่าง "ไม่เคยมี" กับ "ใช้ไม่ได้แล้ว" สถานะ `lost` จึงต้องใช้รายการนี้ iOS ไม่ถามยืนยันตอนสร้างรายการใหม่ ขั้นตอนสร้างกุญแจจึงอ่านกลับหนึ่งครั้ง เพื่อให้รู้ว่าเปิดกุญแจได้จริงก่อนไปต่อ

### บนเว็บ passkey เป็นด่านของแอปตาม ADR 0012

กุญแจอยู่ใน IndexedDB พร้อม credential id ตอนสร้างเรียก `navigator.credentials.create` ด้วย `userVerification: "required"` หลังเช็ก `isUserVerifyingPlatformAuthenticatorAvailable()` ตอนปลดล็อกเรียก `get` ด้วย challenge แบบสุ่ม โดยไม่ตรวจลายเซ็นของ passkey เพราะไม่มี server ที่ต้องเชื่อ และ ADR ยอมรับแล้วว่าด่านนี้ไม่ได้ล็อกตัวกุญแจ

เบราว์เซอร์ต้องการ user gesture ก่อนเรียก passkey หน้าล็อกบนเว็บจึงรอให้กดปุ่ม ส่วนบนมือถือถามทันทีตอนเปิด และมีปุ่มไว้ลองใหม่

### หน้าล็อกใช้ตัวกั้นเดิม

เพิ่มสถานะกุญแจเข้าตัวกั้นใน `src/app` ต่อจากการถือฐานข้อมูล render หน้าที่เกี่ยวข้องแทน `<Stack />` URL จึงไม่เปลี่ยน และกลับหน้าเดิมได้หลังปลดล็อก

polyfill `crypto.getRandomValues` จาก `expo-crypto` ต้องรันก่อน @noble เรียก RNG จึง import เป็นบรรทัดแรกของ root layout

## Risks / Trade-offs

- [มือถือที่ไม่ได้ตั้ง biometric ใช้ไม่ได้] → แอปบอกทางออก และใช้เว็บแทนได้ ถ้ามีคนติดเรื่องนี้จริงค่อยเพิ่ม PIN
- [เปลี่ยน biometric แล้วคนที่มีเครื่องเดียวต้องทำ Pairing ใหม่] → ADR 0012 และ 0048 ยอมรับไว้แล้ว แอปแสดงสถานะ `lost` ชัดเจน
- [Simulator ไม่บังคับ biometric ตามเอกสาร] → Simulator ลองได้แค่ flow ของหน้าจอ ต้องลองบน iPhone จริงก่อน archive
- [@noble หรือ zod อาจทำงานผิดบน Hermes] → ลอง sign แล้ว `verify` บนแอป iOS ก่อนต่อยอด
- [เบราว์เซอร์ลบ IndexedDB ทำให้กุญแจบนเว็บหายแบบแยกจาก "ไม่เคยมี" ไม่ได้] → เรียก `persist()` และยอมให้กลับไปหน้าสร้างกุญแจ ซึ่งต้องทำ Linking หรือ Pairing ใหม่ ตรงกับ ADR 0012 ที่บอกว่าเว็บปลอดภัยน้อยกว่า
- [secret อยู่ใน JS string ระหว่างแปลงจาก base64url จึงล้างไม่หมด] → ล้าง `Uint8Array` เท่าที่ทำได้ ADR 0012 ยอมรับแล้วว่าแอปดึงกุญแจมาใช้เอง

## Open Questions

- **ที่เก็บ `seq` ของ `createSigner`:** `seq` ต้องเดินหน้าตลอด แต่ SQLite บนเว็บหายได้ และ Keychain บน iOS อยู่รอดข้ามการลบแอปขณะที่ SQLite ไม่รอด ถ้าเก็บ `seq` ใน SQLite กุญแจเดิมจะเริ่มเลขใหม่ แล้วซองถูกปฏิเสธว่าเล่นซ้ำ change นี้ยังไม่เซ็นซองจริงจึงไม่กระทบ ให้ `machine-pairing` ตัดสิน โดยน่าจะเก็บไว้ข้างกุญแจแทน
