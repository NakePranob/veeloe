## Context

- Hub ส่ง `recipients` ถึงทุกสายของ Member อยู่แล้ว (`relay/application/service.go`) และรู้จัก Controller จากแถวใน `controller_svc.controllers` ที่มี `member_id` เครื่องที่สองจึงต้องการแค่แถวใหม่ของ Member เดิม แต่วันนี้มีทางเขียนแถวแค่ `POST /pairings` และ Controller ส่ง `recipients` ไม่ได้
- Runtime เก็บ `trust.json` เป็น `{ owners: [{ member, keys }] }` ซึ่งเป็นรายการอยู่แล้ว และตรวจซองด้วย `verify` ที่ทิ้งเลข `seq` ที่ไม่เพิ่มขึ้น
- Controller เก็บ Hub ไว้ในแถว `machine` แต่ละแถว (`hub_url`) และไม่มี Hub เริ่มต้น เครื่องใหม่ที่ยังไม่มี Machine จึงไม่รู้ว่าจะต่อ Hub ไหน แต่เครื่องเดิมรู้
- `task.sync` ดึง event ของ Task ที่อยู่ในฐานข้อมูลบนเครื่องแล้วเท่านั้น ยังไม่มีข้อความที่บอกว่ามี Task อะไรบ้าง
- `machine-pairing`, `controller-device-key` และ `agent-and-task` ยังไม่ archive change นี้ต่อยอดจากโค้ดของทั้งสาม

## Goals / Non-Goals

**Goals:**
- Hub ที่โดนเจาะเพิ่มกุญแจให้ Member, สลับกุญแจของเครื่องใหม่ หรือสลับรายชื่อ Machine ที่เครื่องใหม่ได้รับไม่ได้
- คำสั่งถอนมีผลกับ Machine ที่ปิดอยู่ตอนถอนด้วย และกุญแจที่ถอนแล้วกลับมาไม่ได้แม้ Hub โดนเจาะทีหลัง (ADR 0031)
- จบ change นี้แล้ว Owner Link เบราว์เซอร์จากมือถือ เห็น Machine, Agent และ Task เดิม และถอนเครื่องใดเครื่องหนึ่งได้กับ Hub, Postgres และ Runtime ตัวจริง

**Non-Goals:**
- Linking ด้วย login ทาง email, Invitation, Owner หลายคน และการลบ Member อยู่ใน v0.3
- การหยุดของที่เซ็นไว้แล้วทำงานเอง (Schedule, Idle Work, Watch, Channel, Connector) ยังไม่มีของพวกนี้ใน v0.1 แต่ละ change ที่สร้างมันต้องหยุดเมื่อกุญแจที่เซ็นอยู่ในรายชื่อห้าม
- เปลี่ยนชื่อเครื่องหลัง Link และ push แจ้งเตือน (ADR 0044)

## Decisions

### ลำดับของ Linking

1. เครื่องเดิมเปิด Link เครื่องใหม่ แล้วแสดง `veeloe://link?hub&to&id&secret&exp` เป็น QR และเป็นลิงก์ที่คัดลอกหรือแชร์ได้ `hub` คือ Hub ที่ Machine ของเครื่องนี้อยู่ `to` คือกุญแจของเครื่องนี้ `id` สุ่ม 128 bit และ `secret` สุ่ม 256 bit อายุ 10 นาที
2. เครื่องใหม่สร้างกุญแจ เลือก ใช้กับเครื่องที่มีอยู่แล้ว แล้วสแกน เปิด หรือวางลิงก์ ตั้งชื่อ แล้วส่ง `POST /link-requests` ที่ Hub ในลิงก์ด้วย `{ to, id, key, name, proof }` โดย `proof = HMAC-SHA256(secret, "veeloe-link-request/1" | id | key | name)` จากนั้นต่อ Hub ซ้ำ ซึ่งจะถูกปิดด้วย 4401 จนกว่า Hub จะรู้จัก แบบเดียวกับ Machine ตอน Pairing
3. Hub ตรวจแค่รูปแบบ แล้วส่ง `hub.link_request` ไปที่สายของ `to` ถ้า `to` เป็น Controller ที่ต่ออยู่ ไม่อย่างนั้นตอบ `hub.device_offline` Hub ไม่เก็บอะไร
4. เครื่องเดิมรับคำขอแรกที่ `id` ตรง ยังไม่หมดอายุ และ `proof` ตรงกับรหัสลับ แล้วปิดลิงก์นั้น คำขออื่นไม่แสดงเลย แอปแสดงชื่อเครื่องใหม่ให้เจ้าของอ่านและแก้ได้
5. เจ้าของอนุมัติและยืนยันตัวใหม่ เครื่องเดิมเซ็น `device.link` ของกุญแจในคำขอ แล้วส่ง `POST /links` Hub ลงทะเบียนกุญแจ เก็บใบรับรอง และส่ง `hub.certificates` ให้ทุกสายใน Workspace
6. เครื่องใหม่ผ่าน handshake เครื่องเดิมส่ง `device.handoff` ถึง Member ของตัวเองทุก 3 วินาทีจนได้ `device.linked` หรือหมดอายุ
7. เครื่องใหม่ตรวจค่าพิสูจน์ บันทึก Machine ตอบ `device.linked` แล้วใช้ `agent.list` กับ `task.list` เหมือนเครื่องที่ทำ Pairing

### เครื่องเดิมแสดง QR ที่มี Hub

ADR 0013 เดิมให้เครื่องใหม่แสดง QR แล้วเครื่องเดิมสแกน แต่เครื่องใหม่ยังไม่มี Machine จึงไม่รู้ Hub และต้องมีช่อง Hub ให้กรอกก่อนสร้าง QR ได้ ซึ่งคนส่วนใหญ่ไม่รู้ว่าต้องกรอกอะไร change นี้แก้ ADR 0013 ให้กลับทิศ แบบเดียวกับ Pairing ที่ QR ของ Runtime มี Hub อยู่แล้ว เครื่องเดิมรู้ Hub ของตัวเอง ลิงก์จึงพา Hub ไปให้เครื่องใหม่ ใช้ได้กับ Hub ที่รันเองโดยไม่ต้องตั้งค่าอะไร และเบราว์เซอร์ที่ไม่มีกล้องเปิดหรือวางลิงก์ที่แชร์มาได้

ทิศนี้ทำให้กุญแจใหม่ต้องเดินทางผ่าน Hub แทนที่จะไปจากจอเข้ากล้องตรงๆ คำขอจึงต้องมี HMAC ของรหัสลับที่ไปกับลิงก์ Hub ไม่เคยเห็นรหัสลับ จึงสลับกุญแจ แก้ชื่อ หรือสร้างคำขอขึ้นเองไม่ได้ ผลเท่ากับทิศเดิม และยังไม่ต้องเทียบรหัสสั้น (ADR 0013) เพราะสิ่งที่เดินทางจากจอเข้ากล้องตรงๆ ตอนนี้คือรหัสลับที่ผูกกุญแจไว้แทนตัวกุญแจ

ทางเลือกที่ตัดออก:
- **เครื่องใหม่แสดง QR ตาม ADR 0013 เดิม**: กุญแจใหม่ไปจากจอเข้ากล้องตรงๆ แต่เครื่องใหม่ต้องถาม Hub ซึ่งเป็นช่องที่คนกรอกผิดหรือไม่รู้ค่า และต้องมีค่าเริ่มต้นตอน build ที่ใช้กับ Hub ที่รันเองไม่ได้
- **เครื่องเดิมแสดง QR ที่สองที่มี Hub**: ต้องสแกนสองครั้ง และเครื่องใหม่ต้องมีกล้อง
- **เทียบรหัสสั้นตาม prototype ด้วย**: เพิ่มขั้นตอนที่ไม่ได้กันอะไรเพิ่มในทาง QR เพราะ HMAC กันการสลับกุญแจแล้ว

### Hub ส่งคำขอต่อ ไม่เก็บ

`POST /link-requests` ไม่ต้องยืนยันตัว เพราะ Hub ยังไม่รู้จักกุญแจใหม่ Hub ตรวจรูปแบบ แล้วส่ง `hub.link_request` ไปที่สายของกุญแจ `to` ที่เป็น Controller เท่านั้น Machine หรือกุญแจที่ไม่ได้ต่ออยู่ได้ `hub.device_offline` Hub ไม่เก็บคำขอ เพราะ ADR 0005 บอกว่า Hub ไม่มีคิวข้อความ และคำขอมีความหมายแค่ตอนที่เครื่องเดิมเปิดหน้าแสดง QR อยู่ การตรวจที่นับคือการตรวจบนเครื่องเดิม: `id`, อายุ, ใช้ครั้งเดียว และ HMAC Hub ตรวจสิ่งเหล่านี้ไม่ได้และไม่ต้องตรวจ

ทางเลือกที่ตัดออก: **เครื่องเดิมลงทะเบียน `id` ที่ Hub ก่อน แล้วเครื่องใหม่ส่งคำขอตาม `id`** ไม่ต้องใส่กุญแจของเครื่องเดิมในลิงก์ แต่ Hub ต้องเก็บสถานะต่อลิงก์และต้องมี frame ขาเข้าอีกชนิด ส่วนกุญแจสาธารณะของเครื่องเดิมไม่ใช่ความลับอยู่แล้ว

### Machine ได้กุญแจใหม่จากใบรับรองที่ Hub เก็บไว้

ใบรับรองเป็นของที่เซ็นแยกจากซอง: `{ signed, sig }` โดย `signed` เป็น JSON `{ v, type: "device.link" | "device.revoke", workspace, member, key, by, at, name?, keep? }` และ `sig` เซ็นด้วยกุญแจ `by` แบบ byte ตามที่ส่งจริง (ADR 0019) Hub เก็บไว้ใน `controller_svc.certificates` ตามที่ ADR 0005 กับ 0031 กำหนด แล้วส่ง `hub.certificates` ให้ Machine และ Controller หลัง `hub.ready` ก่อนส่งต่อซองใด และส่งตัวใหม่ทันทีให้สายที่ต่ออยู่ Runtime ตรวจทุกใบเองและใช้ซ้ำได้ผลเดิม

ใบรับรองไม่ใช่ซองเพราะซองมี `seq` ถ้าเครื่องเดิมส่งคำสั่งอื่นหลัง Link แล้ว Machine ที่ปิดอยู่จะได้ใบรับรองที่มีเลขต่ำกว่าเลขล่าสุด และทิ้งเป็นการเล่นซ้ำ

ทางเลือกที่ตัดออก:
- **เครื่องเดิมเซ็นซองเพิ่มกุญแจไปที่ Machine ทีละเครื่อง**: Hub ไม่ต้องเก็บอะไร แต่ Machine ที่ปิดอยู่ได้รับก็ต่อเมื่อเครื่องเดิมเปิดแอปพร้อมกัน ถ้าเครื่องเดิมหายก่อนจะไม่ได้รับเลย และติดเรื่อง `seq` ข้างบน
- **Machine เชื่อรายชื่อ Controller ของ Member จาก Hub**: ง่ายที่สุด แต่ขัดกับ ADR 0013 ที่ให้ Runtime เชื่อเฉพาะกุญแจจาก Pairing หรือ Linking Hub ที่โดนเจาะจะเพิ่มกุญแจของตัวเองได้

### เครื่องใหม่ได้รายชื่อ Machine ผ่านซองถึงตัวเอง

`device.handoff` มี `data` เป็น JSON ของ Workspace, Member, Machine (`id`, `key`, `name`, `hub`) และกุญแจที่ใช้งานของ Member พร้อม `proof = HMAC-SHA256(secret, "veeloe-link/1" | newKey | data)` แบบเดียวกับ `pairingProof` เครื่องใหม่ยังไม่รู้จักกุญแจของเครื่องเดิม จึงตรวจด้วยค่าพิสูจน์แทนลายเซ็น Hub ส่งต่อได้เพราะแก้ `hub-relay` ให้ Controller ส่ง `recipients` ที่มีแค่ Member ของตัวเองได้

ไม่ขัดกับ ADR 0034 เพราะ ADR นั้นกันไม่ให้ Controller เลือกผู้รับแทน Runtime ซึ่งต้องรู้ Grant ส่วนการส่งถึงเครื่องของตัวเองไม่เกี่ยวกับ Grant

ทางเลือกที่ตัดออก: **Hub เก็บ handoff ไว้ให้เครื่องใหม่มารับ** ไม่ต้องแก้ `hub-relay` แต่กลายเป็นคิวข้อความที่ ADR 0005 บอกว่า Hub ไม่มี

### Runtime เก็บ `links` กับ `revoked` ใน `trust.json`

`trust.json` เป็น `{ owners: [{ member, keys }], links: [{ key, by }], revoked: [key] }` ไฟล์เดิมที่ไม่มีสองช่องนี้อ่านเป็นรายการว่าง `links` มีไว้หากุญแจที่หลุดตามตอนถอน การตรวจ `device.link`: `by` อยู่ใน `keys` ของ `member`, `key` ไม่อยู่ใน `revoked`, `workspace` ตรงกับของเครื่อง ถ้า `by` อยู่ใน `revoked` จะรับเฉพาะเมื่อ `key` อยู่ใน `keep` ของคำสั่งถอนที่จดไว้

`pairing.claim` เพิ่มช่อง `keys` ในส่วนที่เซ็น ไม่อย่างนั้น Machine ที่ Pair จากเบราว์เซอร์จะไม่รู้จักมือถือ เพราะใบรับรองชี้จากคนเซ็นไปหาเครื่องใหม่เท่านั้น

### การถอน

- **ถอนจากเครื่องไหน:** เครื่องที่ใช้งานอยู่เครื่องไหนของ Member ก็ได้ รวมถึงเครื่องที่จะถอนเอง ตาม ADR 0031 Owner ถอนเครื่องของ Member อื่นได้ด้วย แต่ v0.1 มี Member คนเดียว
- **`keep` เป็นรายชื่อกุญแจ** ไม่ใช่ hash ของใบรับรอง เพราะกุญแจหนึ่งดอกมีใบ `device.link` ใบเดียว หน้า เครื่องของฉัน ติ๊กเก็บทุกเครื่องไว้เป็นค่าเริ่มต้น เหมือน prototype
- **เครื่องสุดท้าย:** Controller ไม่เซ็น Hub ตอบ `hub.last_device` และ Runtime ไม่ทำตาม Runtime ต้องกันด้วย เพราะ Hub ที่โดนเจาะส่งคำสั่งที่เซ็นถูกแต่ Hub ไม่ยอมรับมาได้ และถ้า Runtime ไม่เหลือกุญแจก็ต้อง `unpair`
- **ซองที่ค้างอยู่:** Hub ปิดสายด้วย 4403 และลบแถวก่อน ซองที่ค้างในคิวขาออกของเครื่องนั้นจึงส่งไม่ได้ ส่วนที่หลุดไปถึง Machine ที่ยังไม่ได้คำสั่งถอน Runtime ทำตามเพราะยังเชื่อกุญแจอยู่ ซึ่งเป็นช่วงสั้นที่ Hub ตัดได้อยู่แล้ว Turn ที่เริ่มไปแล้วทำต่อจนจบ เพราะทำในนามของ Member ที่ยังอยู่ และ Approval ที่รออยู่ตอบจากเครื่องอื่นได้
- **เครื่องที่ถูกถอน:** เมื่อได้ 4403 หรือถอนตัวเองสำเร็จ แอปลบกุญแจและฐานข้อมูลบนเครื่องแล้วกลับไปหน้าสร้างกุญแจ เครื่องที่โดนขโมยอาจไม่เปิดแอปเลย การลบจึงเป็นแค่การเก็บกวาด ไม่ใช่ด่านกัน

ทางเลือกที่ตัดออก: **ถอนกุญแจแล้วเครื่องที่มัน Link หลุดหมดโดยไม่ให้เลือก** ADR 0031 ตัดไว้แล้ว

### เครื่องใหม่เห็น Task เดิมด้วย `task.list`

Controller ส่ง `task.list` ถึงทุก Machine ตอนต่อเข้ามาพร้อม `agent.list` Runtime ตอบ `task.listed` ด้วย `{ id, agent, title, updated }` ของ Task ที่ Member เปิดดูได้ แล้ว Controller ใส่แถวที่ยังไม่มีด้วย `synced_seq = 0` ให้ `task.sync` เดิมดึง event ต่อ ช่วยเครื่องที่ลบแอปแล้วลงใหม่หรือเว็บที่ถูกลบข้อมูล (ADR 0021) ด้วย

ทางเลือกที่ตัดออก: **เครื่องใหม่เห็นแค่ Task ที่เกิดหลัง Link** ไม่ต้องเพิ่มข้อความ แต่เปิดเบราว์เซอร์แล้วไม่เห็นงานที่คุยค้างไว้บนมือถือ ซึ่งเป็นเหตุผลหลักของการ Link

### Controller: รายการเครื่องมาจากใบรับรอง

`entities/device` เก็บตาราง `device(key, member_id, name, linked_by, linked_at, revoked_at)` ที่สร้างจาก `hub.certificates` หลังตรวจลายเซ็น เครื่องแรกคือกุญแจที่ไม่มีใบ `device.link` รายการนี้มีไว้แสดงเท่านั้น คนตัดสินว่าเชื่อกุญแจไหนคือ Runtime Hub ที่โดนเจาะซ่อนเครื่องจากรายการได้ ซึ่งเท่ากับตัดการสื่อสาร ที่ ADR 0006 ยอมรับไว้แล้ว

ตัวสแกน QR ย้ายจาก `pages/add-machine` ไปที่ `shared/ui` เพราะมีที่ใช้สองหน้าแล้ว (Steiger) และ `+native-intent.tsx` รับ `veeloe://link` แล้วเปิดหน้าของเครื่องใหม่ (`/link`) QR บนจอเครื่องเดิมวาดด้วย `uqr` กับ `react-native-svg` ที่มีอยู่แล้ว ปุ่มแชร์ใช้ `Share` ของ React Native จึงไม่มี dependency ใหม่ เครื่องเดิมที่มี Machine บนหลาย Hub ใช้ Hub ของ Machine แรก และเครื่องใหม่ได้แค่ Machine บน Hub นั้น ซึ่งเหมือนเดิม

## Risks / Trade-offs

- [คนที่ได้ลิงก์ไปในช่วงที่ยังไม่หมดอายุ เช่น ถ่ายภาพจอหรือได้ลิงก์ที่แชร์ผิดคน ส่งคำขอได้ และคำขอนั้นผ่าน HMAC] → ลิงก์อย่างเดียว Link เครื่องไม่ได้: เจ้าของต้องเห็นชื่อเครื่องบนเครื่องเดิมแล้วกดอนุมัติพร้อมยืนยันตัวใหม่ ซึ่งตอนนั้นเจ้าของกำลังรอเครื่องใหม่ของตัวเองอยู่ตรงหน้า ลิงก์ใช้ได้ครั้งเดียว คำขอแรกปิดลิงก์ ถ้าคนอื่นส่งก่อน เครื่องจริงของเจ้าของจะส่งไม่ผ่าน และเจ้าของเห็นชื่อที่ไม่รู้จัก ให้ยกเลิกแล้วสร้าง QR ใหม่ ลิงก์หมดอายุใน 10 นาที และเครื่องอื่นของเจ้าของได้รับแจ้งเมื่อมีการ Link จึงถอนได้ทันที ทาง QR ไม่เทียบรหัสสั้นตาม ADR 0013 เพราะ HMAC กัน Hub สลับกุญแจแล้ว ความเสี่ยงที่เหลือคือคนที่ได้ลิงก์ไป ซึ่งรหัสสั้นก็ไม่ได้กัน เพราะคนนั้นอ่านรหัสบนจอของตัวเองได้เหมือนกัน จึงยอมรับได้
- [ลิงก์มีรหัสลับ ถ้าหลุดไปคนอื่นจะส่ง handoff ปลอมให้เครื่องใหม่ได้ก่อน] → ได้แค่หลอกรายชื่อ Machine ซึ่ง Machine เหล่านั้นไม่เชื่อกุญแจใหม่อยู่ดี เพราะต้องมีใบรับรองจากเครื่องเดิม
- [ใครที่รู้กุญแจสาธารณะของ Controller ส่ง `hub.link_request` ถึงสายนั้นได้ ทั้งที่ไม่มีใครเปิด QR อยู่] → เครื่องนั้นทิ้งคำขอที่ไม่ตรงกับ QR ที่แสดงอยู่โดยไม่แสดงอะไร ส่งถี่จนคิวเต็มทำให้สายนั้นหลุดได้ ซึ่งเป็นการตัดการสื่อสารที่ ADR 0006 ยอมรับไว้ ค่อยจำกัดจำนวนครั้งต่อ IP ถ้าเกิดจริง
- [สแกน QR แล้วกดอนุมัติเครื่องของคนอื่น ทำให้คนนั้นได้สิทธิ์เท่าเจ้าของ] → แสดงชื่อเครื่องให้อ่านก่อนอนุมัติ ยืนยันตัวใหม่ และเครื่องอื่นของเจ้าของได้รับแจ้ง จึงถอนได้ทันที
- [Hub ที่โดนเจาะกักคำสั่งถอนไว้ไม่ส่ง Machine] → ADR 0031 ยอมรับไว้สำหรับช่วงก่อน E2E
- [`hub.certificates` โตตามจำนวนครั้งที่ Link และถอน] → v0.1 มี Member คนเดียวและเครื่องไม่กี่เครื่อง ค่อยส่งเฉพาะใบหลังเลขที่ Machine เห็นแล้วเมื่อโตจริง
- [ใบรับรองเก่าของเครื่องที่ถูกถอนยังอยู่ที่ Hub] → ต้องเก็บไว้ ไม่อย่างนั้น Machine ที่ Pair ใหม่จะไม่รู้ว่ากุญแจไหนถูกถอน
- [นาฬิกาของเครื่องใหม่กับเครื่องเดิมไม่ตรงกัน ทำให้ลิงก์ดูหมดอายุ] → เครื่องใหม่เผื่อ 2 นาทีเหมือน Pairing ส่วนเครื่องเดิมตัดตามนาฬิกาของตัวเองซึ่งเป็นคนตั้งเวลาหมดอายุ

## Migration Plan

- `trust.json` เดิมอ่านได้โดยไม่ต้องแปลง และ Runtime รุ่นเก่าข้ามช่อง `keys` ของ `pairing.claim` กับ frame ที่ไม่รู้จัก (ADR 0023)
- migration ของ Hub เพิ่มตารางใหม่อย่างเดียว ถอยกลับด้วย down migration ได้
- Controller เพิ่มตาราง `device` ด้วย migration ใหม่ และเติมเครื่องแรกจากกุญแจของตัวเองเมื่อมี Machine แล้ว
