# Attachment ประกาศ hash ในข้อความที่เซ็นก่อน แล้วส่งตัวไฟล์เป็นก้อนผ่าน Hub ที่ไม่เก็บอะไร

คนจะอยากส่ง screenshot ของ error หรือเอกสารให้ Agent และอยากได้รายงานหรือรูปที่ Agent สร้างกลับมา แต่ Controller และ Runtime คุยกันผ่าน Hub เท่านั้น เพราะทั้งสองฝั่งต่อออกอย่างเดียว (ADR 0001) และ Hub ไม่เก็บเนื้อหา (ADR 0005)

ทางส่งจาก Member ไปหา Agent: Controller ส่งข้อความของ Task ที่เซ็นแล้วก่อน ในข้อความประกาศชื่อ ขนาด และ hash ของทุกไฟล์ แล้วส่งตัวไฟล์ตามเป็นซอง `file.chunk` ก้อนละ 256KB แบบ JSON ที่เข้ารหัสไฟล์เป็น base64 มีช่อง `file` ซึ่งเป็น hash ของทั้งไฟล์ ช่อง `index` และช่อง `total` Hub ส่งต่อตามหัวซองเหมือนซองอื่น Runtime รับเฉพาะก้อนของไฟล์ที่ประกาศไว้ ไม่เกินขนาดที่ประกาศ ต่อกันแล้วเทียบ hash และเริ่ม Turn เมื่อได้ไฟล์ครบ ก้อนจึงไม่ต้องเซ็นทีละก้อน และ Hub สลับไฟล์ไม่ได้ ถ้า Runtime มีไฟล์ hash นั้นอยู่แล้วก็ตอบว่ามีแล้ว ไม่ต้องส่งซ้ำ ไฟล์ละไม่เกิน 20MB ถ้า Machine ออฟไลน์ Hub ปฏิเสธทันที Controller เก็บไว้ในคิวขาออกแล้วส่งใหม่ (ADR 0021) ไฟล์ของ Task ปกติวางที่ `attachments/<task-id>/` ใน Workdir ส่วนของ Task ใน Project วางในโฟลเดอร์ของ Task Agent อ่านด้วย tool ไฟล์ตามปกติ และถ้า model ดูรูปได้ harness ส่งรูปให้ model ตรงๆ

ทางกลับ: Agent เรียก tool `send_file(path)` เพื่อเลือกเองว่าจะส่งไฟล์ไหน แชตแสดงเป็นการ์ดไฟล์ Controller ดึงตัวไฟล์มาเมื่อกดเปิด ด้วยคำขอที่เซ็นแล้ว และ Runtime ตรวจ Grant ก่อนส่ง แบบเดียวกับการ sync ย้อนหลัง (ADR 0034) event log เก็บแค่ชื่อ ขนาด hash และ path (ADR 0018) ใน Channel supervisor ดึงไฟล์จากแชตผ่าน Bot API มาวางที่เดียวกัน และ `send_file` โพสต์ไฟล์เข้าแชต

## Considered Options

- **ส่งไฟล์ทั้งก้อนเป็นข้อความเดียว**: ไม่ต้องหั่นและประกอบ แต่ WebSocket เส้นเดียวกันส่ง Approval กับ Stop ไม่ได้จนไฟล์ส่งเสร็จ Hub ต้องถือทั้งก้อนไว้ในหน่วยความจำ และต้องเซ็น JSON ขนาดหลายสิบ MB
- **ส่งก้อนก่อนแล้วตามด้วยข้อความที่เซ็น**: Turn เริ่มได้ทันทีที่ข้อความมาถึง แต่ระหว่างนั้น Runtime ต้องเก็บก้อนที่ยังไม่มีใครรับรอง ใครส่งก้อนปลอมมาก็ทำให้ดิสก์เต็มได้
- **binary frame ของ WebSocket**: ไม่เสียส่วนเกิน 33% ของ base64 แต่ Protocol จะมีสองรูปแบบ ทั้ง Hub, Controller และ test vector ต้องรองรับทั้งสองแบบ เพิ่มทีหลังได้แบบ additive ถ้าเพดานไฟล์ใหญ่ขึ้นจนคุ้ม
- **อัปโหลดไปพักที่ Hub ผ่าน HTTP**: เส้น WebSocket ไม่ต้องรอ แต่ Hub กลายเป็นที่เก็บเนื้อหา ซึ่งขัดกับ ADR 0005 จนกว่าจะมี E2E
- **ส่งไฟล์ของ Agent ไปหาทุก Controller ทันที**: เปิดดูได้แม้ Machine ปิด แต่ทุกเครื่องโหลดไฟล์ที่อาจไม่มีใครเปิด และ Hub ต้องถือไฟล์รอเครื่องที่ออฟไลน์

## Consequences

- base64 ทำให้ไฟล์ใช้เน็ตมากขึ้นราว 33%
- Runtime ลบไฟล์ที่ได้ไม่ครบเมื่อผ่านไป 1 ชั่วโมง ถ้าสายหลุด Controller ส่งใหม่ทั้งไฟล์ ยังไม่มีการส่งต่อจากจุดที่หลุด
- ถ้า Machine ปิดตอนกดเปิดไฟล์ จะโหลดไม่ได้ ยกเว้นไฟล์ที่อยู่ในแคชของแอปแล้ว
- ไฟล์ใหญ่กว่า 20MB ส่งทาง git หรือ Connector แทน และแอปเปิด PDF หรือ docx ด้วยตัวเปิดไฟล์ของ OS
- `send_file` ใน Channel เป็นทางส่งข้อมูลออกแบบเดียวกับคำตอบ ซึ่ง ADR 0028 ยอมรับไว้แล้ว
- พอมี E2E ค่า `data` ของก้อนเข้ารหัสแบบเดียวกับเนื้อหาอื่น
