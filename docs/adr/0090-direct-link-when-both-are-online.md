# Controller ต่อตรงกับ Machine เมื่อทำได้ Hub เหลือแค่ยืนยันตัว นัดเจอ สะกิด และทางสำรอง

Status: accepted

> แก้ ADR 0001, 0005 และ 0034 บางส่วน ตามที่เขียนไว้ในหัวของแต่ละตัว

ทุกซองระหว่าง Controller กับ Runtime ตอนนี้วิ่งผ่าน Hub (ADR 0001) ทั้ง event ของ Task, การ sync และไฟล์ที่วิ่งสองขา Hub ไม่เห็นเนื้อหา (ADR 0005) และไม่มีคิว ไม่ส่ง push (Runtime ส่ง push เอง) แต่ส่งต่อทุกซองตลอดเวลา จึงเป็นต้นทุนหลักของบริการที่เรา host และเห็น metadata ว่าใครคุยกับเครื่องไหน เมื่อไหร่ และมากแค่ไหน OpenBot (nightly-labs/openbot) ให้มือถือกับเครื่องคุยกันตรงผ่าน WebRTC DataChannel บริการกลางของเขามีแค่บัญชี, Signal สำหรับนัดเจอ และ coturn สำหรับตอนต่อตรงไม่ได้ ต้นทุนกลางของเขาจึงต่ำกว่าเรามาก ถ้าเรายังส่งต่อทุกซอง เราสู้ราคาไม่ได้ เราลดภาระของ Hub ให้ใกล้ระดับนั้น โดยคงสิ่งที่เราดีกว่า คือทุกคำสั่งเซ็นและ Machine ตรวจเอง และ Hub ไม่มีอำนาจอะไร (เจ้าของตัดสิน 2026-11-28)

**ทางตรง** เมื่อ Controller เปิดดู Machine ที่ออนไลน์ Controller ขอต่อ WebRTC DataChannel กับ Runtime โดยแลก offer, answer และ candidate ผ่านสายกับ Hub ที่มีอยู่ ข้อความนัดเจอเซ็นด้วยกุญแจของแต่ละฝั่ง และมี fingerprint ของ DTLS อยู่ในส่วนที่เซ็น Hub จึงสวมรอยเป็นปลายทางไม่ได้ ระหว่างต่อตรงอยู่ event ของ Task, การ sync, คำสั่ง และไฟล์ทั้งหมดวิ่งทางตรง

**ลายเซ็นเหมือนเดิม** สิ่งที่วิ่งทางตรงคือ envelope ที่เซ็นแล้วแบบเดียวกับที่ผ่าน Hub Runtime ตรวจลายเซ็น, `seq` และ Grant เหมือนเดิม และไม่ถือว่าช่องทางที่เข้ารหัสเป็นการยืนยันตัว (ADR 0006)

**สะกิดแทนส่ง event** Runtime ไม่ส่ง event ของ Task ผ่าน Hub ไปหาทุกเครื่องของผู้รับอีกต่อไป (เปลี่ยน ADR 0034 ส่วนการส่ง) ผ่าน Hub ส่งแค่ซองสะกิดเล็กๆ ที่บอกว่า Agent ไหนมีของใหม่ถึง `seq` ไหน โดยไม่มีเนื้อหา Controller ที่ได้สะกิดตอนเปิดแอปอยู่ ต่อตรงแล้ว sync เอง (spec `task-sync`) ส่วนที่ไม่ได้เปิดแอปใช้ push ที่ Runtime ส่งอยู่แล้ว (ADR 0044) แล้ว sync ตอนเปิด การเลือกผู้รับจาก Grant ยังทำที่ Runtime เหมือนเดิม

**รับซองที่สลับลำดับได้ครั้งเดียว** ซองที่ส่งทางหนึ่งอาจถึงหลังซองถัดไปที่ส่งอีกทาง ผู้รับจึงไม่ปฏิเสธเลขที่ต่ำกว่าเลขล่าสุดอีกแล้ว แต่รับเลขที่ไม่เคยรับในหน้าต่าง 1024 เลขล่าสุดของรอบนี้ (spec `protocol-envelope`) เลขที่เก็บลงดิสก์ยังเป็นเลขสูงสุดเลขเดียว หลังเริ่มใหม่จึงปฏิเสธทุกเลขที่ไม่มากกว่าเลขนั้นเหมือนเดิม Machine ส่งซองถึง Member ผ่าน Hub ด้วยเมื่อเครื่องใดของ Member นั้นยังไม่มีทางตรง และเครื่องที่ได้ซองทั้งสองทางรับครั้งเดียว ก่อนปิดทางตรง Controller ส่ง `direct.close` บนทางตรงแล้วอ่านต่ออีกครู่หนึ่ง Machine จึงเลิกเขียนบนทางนั้นก่อนที่ทางจะปิดจริง

**ทางสำรองคือ Hub** ถ้าต่อตรงไม่ติด หรือเครือข่ายบล็อก UDP คำสั่งและ event ที่ต้องเห็นทันที เช่น Approval และข้อความในแชตที่เปิดอยู่ ส่งผ่าน Hub แบบเดิม ข้อความที่ส่งไปทางหนึ่งแล้วไม่ส่งซ้ำอีกทาง Runtime เรียงด้วย `seq` และทิ้งตัวซ้ำ เราไม่ตั้ง TURN แยก เพราะ Hub ส่งต่อแบบไม่เห็นเนื้อหาอยู่แล้ว

**ไฟล์ใหญ่ไม่ผ่านทางสำรอง** ไฟล์ที่ใหญ่เกิน 1 MB (Attachment ที่ส่งไปและไฟล์ที่ Agent ส่งกลับ) วิ่งทางตรงเท่านั้น ถ้าต่อตรงไม่ได้ Controller แสดงว่ากำลังรอทางตรงและลองใหม่เอง ไฟล์เล็กกว่านั้นผ่านทางสำรองได้

**ในวง LAN** Runtime ประกาศตัวด้วย mDNS ด้วยรหัสของ Machine เท่านั้น ไม่มีชื่อ Agent หรือ Workspace Controller ที่จับคู่ไว้แล้วต่อตรงในวงเดียวกันได้แม้ Hub ล่ม ส่วน Pairing, Invitation และ Linking ยังทำผ่าน Hub

**Hub เหลือหน้าที่** ยืนยันกุญแจของสาย, กั้นให้อยู่ใน Workspace เดียวกัน, นัดเจอ, ส่งซองสะกิด, ทางสำรอง, ที่นัดเจอของ Pairing และ Linking, ตัดสายของกุญแจที่ถูกถอน, เก็บชื่อ Member และ Webhook ตาม ADR 0086 Hub ไม่มีคิว ไม่ส่ง push และไม่มีอำนาจตัดสินสิทธิ์ เหมือนเดิม

**Hub ตอบ STUN เอง** Hub ตอบ STUN Binding บน UDP port 3478 ของ host เดียวกับ URL ของ Hub ทั้ง Runtime และ Controller ถามที่นั่น จึงได้ที่อยู่ที่เน็ตเห็นมาใส่ใน offer และ answer และต่อตรงข้ามเราเตอร์ได้ STUN ไม่ส่งต่อข้อมูลใดๆ มันแค่บอกผู้ถามว่าเห็นมาจากที่อยู่ไหน และคำตอบยาวกว่าคำถามแค่ไม่กี่ byte เราไม่มี TURN NAT สองฝั่งที่เปลี่ยน port ตามคู่ที่คุยด้วย (มือถือบางเครือข่าย) จึงยังต่อตรงไม่ได้ และกรณีนั้นใช้ Hub เป็นทางสำรอง (เจ้าของตัดสิน 2026-11-28)

## Considered Options

- **ไม่มี Hub แบบ P2P ล้วน**: ยังต้องมีที่นัดเจอข้ามเน็ตอยู่ดี และตัดสายกุญแจที่ถูกถอนไม่ได้
- **ใช้ coturn แยกแบบ OpenBot**: เพิ่มบริการที่ต้องดูแล โดยได้แค่สิ่งที่ Hub ทำอยู่แล้ว
- **ต่อตรงแต่ยังส่ง event ผ่าน Hub ไปทุกเครื่อง**: ง่ายกว่า แต่ภาระหลักของ Hub แทบไม่ลด
- **คงทุกอย่างผ่าน Hub**: ง่ายสุด แต่ต้นทุนกลางสูงกว่าคู่แข่งมาก และ Hub เห็น metadata ทั้งหมด

## Consequences

- Hub ที่ deploy ต้องเปิด UDP 3478 (`HUB_STUN_ADDR`) บน host เดียวกับ URL ของ Hub ถ้า Hub อยู่หลัง proxy ที่รับแค่ HTTP ทางตรงข้ามเน็ตจะใช้ไม่ได้ และในวงเดียวกันยังใช้ได้
- ใช้ STUN ของคนอื่น (เช่น Google) ไม่ได้เลือก เพราะจะบอกบริการภายนอกว่าเครื่องไหนกำลังต่อตรงเมื่อไหร่
- iOS ตัดการเชื่อมต่อตอนแอปอยู่เบื้องหลัง ทางตรงจึงมีแค่ตอนเปิดแอป ต่อใหม่ใช้เวลาไม่กี่วินาที ระหว่างนั้นใช้ทางสำรอง
- Controller ที่ไม่ได้เปิดอยู่ไม่ได้ event สดอีกแล้ว Inbox อัปเดตเมื่อเปิดแอปหรือได้ push ซึ่งตรงกับพฤติกรรมของมือถืออยู่แล้ว
- องค์กรที่บล็อก UDP ใช้ทางสำรองตลอด ไฟล์ใหญ่ส่งไม่ได้จนกว่าจะต่อตรงได้ ข้อนี้ต้องบอกในแอป
- ต้องแก้ spec `hub-relay` (ซองสะกิด), `task-sync` (sync ทางตรง) และ `task-attachments` (ไฟล์ใหญ่ทางตรงเท่านั้น)
- Runtime ต้องมี WebRTC (`webrtc-rs`) และ Controller ต้องมี `react-native-webrtc` ซึ่งเป็น native module
- ต้องมี e2e ที่ส่งข้อความสลับสองทางแล้วลำดับยังถูกและไม่มีตัวซ้ำ และ e2e ที่ Hub ไม่ได้รับซองที่มีเนื้อหาระหว่างต่อตรง ก่อนเปิดใช้จริง
