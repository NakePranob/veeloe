# Team อยู่บน Machine เดียว และ Agent ในทีมอ่าน Workdir ของกันได้ระหว่างทำ Task ของทีม

Agent ทุกตัวใน Team ต้องอยู่บน Machine เดียวกับ Entry Delegation จึงเกิดอยู่ภายใน Runtime ตัวเดียว ไม่ผ่าน Hub Team กับ Flow เก็บตัวจริงที่ Runtime และแก้ได้ด้วยคำสั่งที่ Controller เซ็นเท่านั้น (ADR 0006) Runtime เป็นคนตรวจเส้น เพดาน และ Grant เอง ส่วน Hub ไม่รู้จัก Flow และส่งต่อข้อความระหว่าง Controller กับ Runtime อย่างเดียว เหตุผลหลักคือไฟล์ งานของทีมส่วนใหญ่ส่งต่อกันเป็นไฟล์ เช่นโค้ด ร่างบทความ หรือไฟล์ข้อมูล แต่ Delegation ส่งได้แค่ข้อความ ถ้าทีมข้ามเครื่อง ไฟล์ต้องไปทาง git หรือที่เก็บกลางที่ทุกเครื่องเข้าถึงได้ หรือต้องวิ่งผ่าน Hub ซึ่งขัดกับ ADR 0005

เมื่อทีมอยู่เครื่องเดียวกัน Agent ใน Team เดียวกันอ่าน Workdir ของกันได้ แต่เขียนได้แค่ของตัวเอง และอ่านได้เฉพาะตอนที่ Turn นั้นอยู่ใน Task ของ Team นั้น supervisor เปิด worker ใหม่ด้วยสิทธิ์อ่านชุดใหม่เมื่อ Turn ถัดไปต้องใช้สิทธิ์ต่างจากเดิม ซึ่งการครอบ sandbox เพิ่มเวลาแค่ราว 16 ms (ADR 0008) คนที่เริ่ม Task กับ Team มี Use ที่ Agent ทุกตัวในทีมอยู่แล้ว (ADR 0010) การอ่านจึงตรงกับสิทธิ์ของเขา ถ้าอ่านได้ตลอด Member ที่มี Use แค่ตัวเดียวจะคุยกับ Agent ตัวนั้นตรงๆ แล้วให้อ่าน `.env` ของเพื่อนร่วมทีมได้ และ Agent ที่อยู่สองทีมจะกลายเป็นสะพานส่งไฟล์ข้ามทีม Workdir หนึ่งจึงยังมีคนเขียนคนเดียวตาม ADR 0011 reviewer เปิดดูไฟล์ที่ frontend แก้ได้ตรงๆ และแก้แทนไม่ได้ ต้องตีงานกลับให้ frontend แก้เอง ความรับผิดชอบจึงชัดว่าไฟล์ไหนเป็นงานของใคร นอกจากนี้ Delegation, Stop ที่ไหลลงทั้งสาย และการนับเพดาน กลายเป็นเรื่องภายในเครื่องเดียว ต้นไม้ของ Task ทั้งทีมอยู่บนเครื่องเดียว และภัยตาม ADR 0003 ที่ Agent ที่โดนหลอกสั่ง Agent บนเครื่องที่มีสิทธิ์สูงกว่า เช่น deployer บน production ก็หายไป เพราะทั้งทีมอยู่ในขอบเขตความไว้ใจเดียวกัน

ทีมข้ามเครื่องยังเป็นเป้าหมาย และเพิ่มทีหลังได้แบบ additive (ADR 0023) เมื่อตอบได้ว่าไฟล์จะข้ามเครื่องยังไง ตอนนั้น Hub ต้องกลับมาตรวจเส้นและตรวจว่า Agent ต้นทางอยู่บน Machine ที่ส่งมาจริง และ Runtime ต้องเซ็น Delegation ที่ส่งออก

## Considered Options

- **ทีมข้ามเครื่องผ่าน Hub**: เป็นจุดที่ทำให้ Veeloe ต่างจาก multi-agent บนเครื่องเดียว และส่งงานจากทีม dev ไปถึง deployer บน production ได้ แต่ไฟล์ข้ามเครื่องไม่ได้ ต้องพึ่ง git หรือที่เก็บกลาง และต้องใส่ปลายทางนั้นไว้ใน Egress ของทุกเครื่อง
- **แนบไฟล์ไปกับ Delegation ผ่าน Hub**: ขัดกับ ADR 0005 เพราะ Hub จะกลายเป็นทางผ่านของไฟล์ลูกค้าทุกชิ้น และค่า bandwidth เป็นต้นทุนของเรา ขณะที่รายได้คิดตามจำนวน Machine (ADR 0001)
- **ทีมมีโฟลเดอร์กลางที่ทุกตัวเขียนได้ หรือทั้งทีมใช้ Workdir เดียว**: ไม่ต้องหาว่าไฟล์อยู่ไหน แต่มีหลายตัวเขียนที่เดียวกัน ซึ่งขัดกับ ADR 0011 และพอส่งงานให้หลายตัวพร้อมกันได้ (ADR 0003) ไฟล์ก็ทับกันจริง

## Consequences

- ความลับที่อยู่ใน Workdir เช่น `.env` หรือ token เพื่อนร่วมทีมยังอ่านได้ระหว่างทำ Task ของทีม และระหว่างนั้นคัดลอกไปไว้ใน Workdir ของตัวเองได้ ซึ่งจะค้างอยู่ให้ Task อื่นเห็น Controller ต้องบอกให้ชัดตอนเพิ่ม Agent เข้า Team
- Agent ที่มี Channel อยู่ใน Team ไม่ได้ (ADR 0028)
- การใส่หรือเอา Agent ออกจาก Team ต้องมี Manage ที่ Agent ตัวนั้น และการลบ Team ต้องมี Manage ที่ Agent ทุกตัวในทีม (ADR 0010)
- ถ้าหลาย Agent ในทีมทำงานกับ repo เดียวกัน เช่น frontend กับ backend แต่ละตัว clone repo ไว้ใน Workdir ของตัวเอง แล้วรวมงานด้วย `git fetch` จาก Workdir ของเพื่อนร่วมทีมระหว่างทำ Task ของทีม ไม่ต้องมีสิ่งที่เรียกว่า Project เพิ่ม
- ทีม dev ส่งงานต่อให้ deployer ที่อยู่บนอีกเครื่องไม่ได้ Member ต้องไปสั่ง deployer เองแบบคุยเดี่ยว
- Controller อ่าน Team กับ Flow จาก Runtime แล้วเก็บไว้บนเครื่อง (ADR 0021) ถ้า Machine ดับ จะเห็นได้แค่ที่เคยเก็บไว้ และแก้ Team ไม่ได้จนกว่าเครื่องจะกลับมา เพราะ Hub ไม่มีคิว (ADR 0005) Controller ที่เพิ่ง Linking ตอนเครื่องดับจะยังไม่เห็น Team ของเครื่องนั้นเลย
- ถ้า Machine พังหรือลงระบบใหม่ Team ของเครื่องนั้นหายไปพร้อมกับ Agent และประวัติ Task (ADR 0005) หลัง Pairing ใหม่และสร้าง Agent ใหม่แล้ว Controller เสนอสร้าง Team เดิมขึ้นใหม่จากที่เก็บไว้ โดยให้ Member จับคู่ Agent เก่ากับตัวใหม่แล้วเซ็นคำสั่งใหม่ ส่งคำสั่งเดิมที่เซ็นไว้ซ้ำไม่ได้ เพราะ Agent บนเครื่องใหม่เป็นตัวใหม่
- คำโปรยว่า Agent ทำงานร่วมกันเป็นทีมข้ามเครื่อง เปลี่ยนเป็นสิ่งที่จะทำ ไม่ใช่สิ่งที่ทำได้แล้ว
