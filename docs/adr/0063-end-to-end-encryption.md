# E2E เข้ารหัสระหว่าง Controller กับ Runtime และ Runtime เข้ารหัสประวัติให้กุญแจใหม่ตอน sync

ก่อนมี E2E คนที่เข้าถึง Hub ได้ยังเห็นเนื้อในตอนข้อความวิ่งผ่าน ซึ่ง ADR 0005 รับได้เฉพาะช่วง v0.1 และกำหนดให้เสร็จก่อนเปิดให้คนอื่นใช้ ปลายทางของการเข้ารหัสคือ Controller กับ Runtime Runtime ถือเนื้อหาแบบอ่านได้เพราะ Agent ต้องใช้ E2E ของเราจึงกัน Hub ไม่ได้กัน Provider ที่รับ prompt เจ้าของ Machine หรือ Telegram ที่รับข้อความของ Channel แอปและการตลาดต้องพูดว่า "Hub อ่านไม่ได้" ไม่ใช่ "มีแค่ผู้รับที่อ่านได้"

สิ่งที่เข้ารหัสคือเนื้อหาของ Task ทั้งหมด รวมถึง Attachment (ADR 0050) ชื่อและสรุปของเส้น (ADR 0061) Runtime เลือกผู้รับจาก Grant (ADR 0034) และกฎการเปิดดู Task (ADR 0060) แล้วเข้ารหัสให้กุญแจของทุก Controller ของคนเหล่านั้น หัวซองยังอ่านได้ คือผู้ส่ง รายชื่อผู้รับ รหัส Task และเวลา Controller แต่ละเครื่องมีกุญแจถอดรหัสของตัวเองซึ่งแยกจากกุญแจเซ็น กุญแจเซ็นล็อกด้วย Face ID (ADR 0012) จึงใช้ถอดรหัส push ตอนจอล็อกไม่ได้ กุญแจถอดรหัสถูกรับรองด้วยกุญแจเซ็นของเครื่องนั้น

Hub ไม่เก็บเนื้อหา และประวัติอยู่ครบบน Runtime (ADR 0005) คนหรือเครื่องที่เข้ามาใหม่จึงอ่านประวัติที่ตัวเองมีสิทธิ์ได้ (เจ้าของตัดสิน 2026-11-01): เมื่อขอ sync ด้วยคำขอที่เซ็น Runtime ตรวจสิทธิ์ตาม ADR 0034 แล้วเข้ารหัสให้กุญแจของเครื่องที่ขอ ซึ่งตรงกับ ADR 0021 ที่ให้ sync จากเลข 0 ได้ทุกเมื่อ และ ADR 0005 ที่ให้รองรับเครื่องที่เพิ่มด้วย Linking การปิดกั้นประวัติแบบ Signal ไม่ได้ทำให้ปลอดภัยขึ้น เพราะ Hub อ่านไม่ได้อยู่แล้ว

เมื่อกุญแจถูกถอน Runtime เลิกใส่กุญแจนั้นในรายชื่อผู้รับ จึงไม่ต้องหมุนกุญแจกลาง Machine ที่ออฟไลน์ตอนถอนรับคำสั่งถอนที่เซ็นแล้วจาก Hub ตอนต่อเข้ามา (ADR 0031)

## Considered Options

- **กุญแจกลางของ Workspace**: ง่ายสุด แต่เครื่องเดียวหลุดอ่านได้ทุกอย่าง และถอนสมาชิกคนหนึ่งต้องหมุนกุญแจทั้ง Workspace
- **session แบบ Signal ต่อคู่อุปกรณ์**: มี forward secrecy แต่ต้องมี handshake และ ratchet เก็บไว้เป็นงานอนาคต
- **คนใหม่และเครื่องใหม่อ่านประวัติเก่าไม่ได้**: ดูปลอดภัยกว่า แต่เครื่องใหม่จะเจอแชตว่าง และคนใหม่ต้องให้คนเก่าคัดงานมาแปะ โดยไม่ได้ความปลอดภัยเพิ่ม
- **E2E เฉพาะแชต 1:1**: ง่ายกว่า แต่ Hub ยังเห็นงานจริงของ Project

## Consequences

- ไม่มี forward secrecy ใครได้กุญแจถอดรหัสของเครื่องหนึ่ง พร้อมกับข้อความเข้ารหัสที่ดักเก็บไว้ จะอ่านข้อความที่ส่งให้เครื่องนั้นได้
- กุญแจถอดรหัสต้องอ่านได้ตอนแอปอยู่เบื้องหลัง จึงป้องกันได้น้อยกว่ากุญแจเซ็น
- Hub ที่โดนเจาะกักคำสั่งถอนได้ เครื่องที่ถูกถอนจึงอาจยังได้เนื้อหาจาก Runtime ที่ไม่ได้รับคำสั่งถอน ADR 0031 รับข้อนี้ไว้เฉพาะก่อน E2E วิธีแก้ยังเปิดอยู่และต้องตอบก่อนสร้าง E2E
- ความไว้ใจทั้งหมดอยู่ที่ใบรับรองกุญแจ การเทียบรหัสตอน Invitation และ Linking จึงสำคัญ
- ถ้า Machine พังและไม่มี backup ประวัติส่วนที่ไม่อยู่บน Controller หายไป (ADR 0005)
- คนที่เคยมีสิทธิ์ยังเก็บสำเนาบนเครื่องตัวเองได้
- ซองปัจจุบันมี `to` เป็นค่าเดียว รายชื่อผู้รับกับกุญแจที่ห่อต่อเครื่องต้องเพิ่มเข้า Protocol แบบ additive (ADR 0023) พร้อม test vector
- Hub ยังเห็น metadata ว่าใครคุยกับใคร เมื่อไหร่ และมากแค่ไหน (ADR 0005)
