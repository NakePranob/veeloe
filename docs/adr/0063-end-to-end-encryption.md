# เข้ารหัสต้นทางถึงปลายทาง (E2E) เนื้อหา Task อ่านได้เฉพาะคนในรายชื่อผู้รับ

วันนี้เนื้อในของ Task ป้องกันด้วย TLS อย่างเดียว คนที่เข้าถึง Hub ได้ยังเห็นเนื้อในตอนข้อความวิ่งผ่าน ซึ่ง ADR 0005 ยอมรับไว้เฉพาะช่วง v0.1 ที่มีแค่ Owner คนเดียว และกำหนดว่า E2E ต้องเสร็จก่อนเปิดให้คนอื่นใช้ ADR 0034 วางโครงไว้แล้วว่า Runtime เลือกผู้รับจาก Grant ที่ตัวเองถือ ใส่รายชื่อไว้ในหัวซอง และวันที่มี E2E ให้ Runtime เข้ารหัสเนื้อหาให้เฉพาะกุญแจของคนในรายชื่อ ADR ฉบับนี้ตอบว่าเข้ารหัสอะไร ให้ใคร ด้วยกุญแจของใคร หมุนกุญแจอย่างไร และ Hub ยังเห็นอะไร

สิ่งที่เข้ารหัสคือเนื้อหา Task และข้อความทั้งหมด เข้ารหัสให้เฉพาะรายชื่อผู้รับที่ Runtime เลือกตอนส่ง (ADR 0034) คือคนที่มี Use ขึ้นไปที่ Agent นั้นสำหรับ event ของ Task คนที่มี Approve ขึ้นไปสำหรับ push ของ Approval (ADR 0044) คนที่เริ่ม Task คนที่ถูก Mention คนที่ตั้ง Schedule หรือ Manager ตามตาราง ADR 0044 ส่วนหัวซองยังอ่านได้เหมือนเดิม คือผู้ส่ง รายชื่อผู้รับ รหัส Task และเวลา Hub ยังอ่านหัวซองเพื่อส่งต่อได้โดยไม่ต้องรู้ Grant ตาม ADR 0005

กุญแจที่ใช้เป็นกุญแจรายคนรายเครื่อง (per-member per-device) ต่อจาก ADR 0013 ที่ให้สมาชิกยืนยันตัวด้วยกุญแจ ไม่มีรหัสผ่าน และ ADR 0012 ที่ให้แต่ละเครื่องมีกุญแจของตัวเอง Controller แต่ละเครื่องมีกุญแจของตัวเอง ไม่มีกุญแจกลางของ Workspace ที่ทุกคนใช้ร่วมกัน ถ้าเครื่องหนึ่งหลุด ประวัติเก่าจะไม่รั่วทั้งหมด แลกกับความซับซ้อนที่ต้องเข้ารหัสเนื้อหาชิ้นหนึ่งให้หลายกุญแจ (รายคนคูณรายเครื่อง) แทนที่จะเข้ารหัสครั้งเดียวด้วยกุญแจกลาง

เมื่อสมาชิกถูกถอนออกหรือกุญแจเครื่องหนึ่งถูกถอน (ADR 0031) เนื้อหาใหม่ใช้กุญแจชุดใหม่ คนที่ถูกถอนอ่านเนื้อหาใหม่ไม่ได้ ส่วนเนื้อหาเก่ายังอ่านได้โดยคนที่เคยอ่านได้อยู่แล้ว ไม่มีการเข้ารหัสเก่าซ้ำย้อนหลัง เครื่องที่ออฟไลน์ตอนหมุนกุญแจรับรายชื่อถอนกุญแจที่เซ็นแล้วซึ่ง Hub เก็บเป็น metadata ไว้ตอนต่อเข้ามาใหม่ ตาม ADR 0005 กับ ADR 0031

บริบทกลุ่ม ทั้ง Channel ที่ผูกไว้ (ADR 0028) ห้อง Project (ADR 0045, 0046) และห้องย่อยส่วนตัวในบริบทกลุ่ม (ADR 0060) ใช้กฎเดียวกัน คือรายชื่อผู้รับต่อข้อความ มาจาก Grant ที่มีอยู่ตอนส่ง คนที่เข้าห้องทีหลังอ่านเนื้อหาเก่าไม่ได้ เพราะตอนส่งยังไม่มีชื่อเขา สอดคล้องกับกฎไม่ซ่อนย้อนหลังของ ADR 0060

Hub ยังเห็นแค่หัวซองเหมือนวันนี้ ไม่เปลี่ยน ADR 0005 push ยังไม่มีเนื้อหาติดไป ไม่เปลี่ยน ADR 0044 วันที่มี E2E ให้ push พกข้อความที่เข้ารหัสแล้วตามที่ ADR 0005 วางไว้

## Considered Options

- **กุญแจกลางของ Workspace ทุกคนใช้ร่วมกัน**: ง่ายสุด เข้ารหัสครั้งเดียวทุกคนอ่านได้ หมุนกุญแจก็แค่แจกกุญแจใหม่ แต่เครื่องเดียวหลุดประวัติทั้งหมดรั่ว และถอนสมาชิกคนหนึ่งต้องหมุนกุญแจทั้ง Workspace ทุกครั้ง จึงไม่เลือก
- **เปิด session แบบ Signal รายคู่อุปกรณ์ (per-device sessions)**: ปลอดภัยสูงสุด มี forward secrecy ข้อความเก่าปลอดภัยแม้กุญแจปัจจุบันหลุด แต่ซับซ้อนสุด ต้องมี handshake, ratchet และการ sync session ข้ามเครื่องของคนเดียวกัน เก็บไว้เป็นงานอนาคต ไม่ใช่รอบแรกของ E2E
- **E2E เฉพาะแชต 1:1 เนื้อหากลุ่มของ Channel กับ Project ไม่เข้ารหัส**: ง่ายกว่าเพราะกลุ่มมีรายชื่อผู้รับเปลี่ยนบ่อย แต่เนื้อหากลุ่มคือเนื้องานจริงของ Project ถ้าไม่เข้ารหัส Hub ก็ยังเห็นงานทั้งหมด E2E จะไม่มีความหมาย จึงเข้ารหัสกลุ่มด้วยกฎรายชื่อผู้รับต่อข้อความเดียวกัน

## Consequences

- v0.1 ไม่โดนบล็อก E2E อยู่ใน v0.3 (ADR 0048) แต่โค้ดใหม่ตั้งแต่ v0.1 ต้องใส่รายชื่อผู้รับในหัวซองทุกครั้ง (ADR 0034) เพื่อให้วันหนึ่งเติมการเข้ารหัสได้โดยไม่ต้องเปลี่ยน protocol (ADR 0023)
- E2E ต้องเสร็จก่อนเปิดให้คนอื่นใช้ ตามที่ ADR 0005 กำหนดไว้แล้ว ADR นี้แค่ตอบว่าทำอย่างไร
- ทำกุญแจหายทุกเครื่อง เท่ากับเสียเนื้อหาเก่า เว้นแต่ยังมีอีกเครื่องที่อ่านได้ให้เข้ารหัสใหม่ ทางกลับเข้ามาใช้การเชิญใหม่ตาม ADR 0031 แล้วเริ่มด้วยกุญแจชุดใหม่ เนื้อหาเก่าที่ไม่มีเครื่องไหนอ่านได้แล้วกู้คืนไม่ได้
- approval payload จากห้องส่วนตัว (ADR 0060) เข้ารหัสให้เฉพาะคนอนุมัติ คนที่ไม่ใช่คนอนุมัติเปิดไม่ออกแม้ Hub ส่งหัวซองถึงมือ
- คนเข้าห้อง Project หรือ Channel ทีหลังอ่านเนื้อหาเก่าไม่ได้ ต้องให้สมาชิกเดิมสรุปหรือคัดส่วนที่เกี่ยวข้องมาแปะใหม่
- Hub ยังเห็น metadata ว่าใครคุยกับใคร เมื่อไหร่ มากแค่ไหน เหมือนเดิม (ADR 0005) E2E ซ่อนแค่เนื้อหา ไม่ซ่อนความสัมพันธ์
