# Agent แสดงการ์ดในแชตได้จากชุดที่กำหนดไว้เท่านั้น และ Runtime ตรวจทั้งรูปแบบและที่มาของตัวเลข

> แก้ ADR 0044 บางส่วน ตามที่เขียนไว้ในหัวของ ADR นั้น

ตอนนี้ทุกการ์ดใน Task มาจากชนิดของ event ที่ Runtime สร้างเอง เช่น Approval, ไฟล์, ไฟล์ที่เปลี่ยน, Budget และ Compaction Agent สื่อสารได้แค่ข้อความ Markdown คำถามที่มีตัวเลือก ตัวเลขที่ต้องเทียบ และแผนงานยาวๆ จึงกลายเป็นย่อหน้าที่อ่านยากบนมือถือ OpenBot (nightly-labs/openbot) มีสองแบบ คือการ์ดตายตัว (ยืนยัน, ตัวเลือก, ฟอร์ม, แผน, ขอ key) และหน้า HTML ที่ Agent เขียนเองซึ่งเปิดใน sandbox ทั้งสองวาดได้ทั้งบนเดสก์ท็อปและมือถือ เราเลือกแค่การ์ดตายตัว และวาดแบบ native บน Controller (เจ้าของตัดสิน 2026-11-27)

**ชุดการ์ดตายตัว** Agent เรียก tool ของการ์ดพร้อม JSON ชุดแรกมีห้าชนิด:

| tool | แสดงอะไร | เพดาน |
|---|---|---|
| `ask_choice` | Question หนึ่งข้อ มีตัวเลือก และพิมพ์ตอบเองได้เสมอ | ตัวเลือกไม่เกิน 4 ข้อ |
| `ask_form` | Question ที่ตอบเป็นช่องสั้นๆ ได้แก่ ข้อความ ตัวเลข ตัวเลือก และวันที่ | ไม่เกิน 6 ช่อง ไม่มีช่องลับ |
| `show_table` | ตารางที่เลื่อนซ้ายขวาได้ในการ์ด | 6 คอลัมน์ × 50 แถว |
| `show_numbers` | ตัวเลขสำคัญ แต่ละตัวมีค่าที่เปลี่ยนและที่มา | ไม่เกิน 4 ตัว |
| `show_plan` | checklist ของงานที่ Agent ติ๊กเองระหว่างทำ | ไม่เกิน 12 ข้อ |

**Runtime ตรวจก่อนเขียน** ค่าที่ไม่ตรง schema หรือเกินเพดานไม่ถูกวาด tool ตอบ Agent ว่าผิดที่ช่องไหน Agent จึงแก้แล้วเรียกใหม่ได้ ที่ผ่านแล้วเขียนลง Task log เป็น event `card.shown` (ADR 0018) ซึ่งมี `id`, ชนิด, เลข version ของ schema, ค่าที่ตรวจแล้ว และ `fallback` ซึ่งเป็นข้อความเปล่าที่ Runtime สร้างจากค่า Controller รุ่นที่ไม่รู้จักชนิดนั้นแสดง `fallback` แทน (ADR 0023) และ Channel ก็ส่ง `fallback` จนกว่าจะทำปุ่มของแต่ละแชต `show_plan` ที่ส่ง `id` เดิมซ้ำเขียน event `card.updated` และการ์ดใบเดิมเปลี่ยนตาม ไม่ขึ้นใบใหม่

**แผนต้องปิดครบก่อนจบ Turn** ข้อในแผนมีสถานะ รอ, กำลังทำ, เสร็จ, ติดขัด และข้าม ติดขัดกับข้ามต้องบอกเหตุผล ถ้า Agent จะจบ Turn ทั้งที่ยังมีข้อที่รอหรือกำลังทำ Runtime ไม่จบให้ และส่งข้อความกลับไปบอกว่าข้อไหนยังไม่ปิด ได้ไม่เกิน 2 ครั้งต่อ Turn ถ้ายังไม่ปิดอีก Turn จบ และการ์ดแสดงข้อที่ค้างว่า "ไม่ได้ปิด" กฎนี้ใช้กับทุก Turn รวมถึงรอบที่ทำงานเองโดยไม่มีคนเฝ้า ซึ่งเป็นที่ที่สำคัญที่สุด เพราะไม่มีใครเห็นว่า Agent ทำไม่ครบ OpenBot ส่งข้อความกลับให้ทำต่อแบบเดียวกันได้ถึง 8 ครั้ง แต่ยกเว้นรอบของ routine ของเราใช้กับรอบที่ไม่มีคนเฝ้าด้วย

**ที่มาของตัวเลข Runtime ตรวจได้** ทุกตัวใน `show_numbers` และทุก `show_table` บอกที่มาเป็นหนึ่งในสามแบบ คืออ่านมา, คนบอก หรือ Agent เดาเอง แบบอ่านมาต้องอ้างถึง tool call ใน Turn เดียวกันที่อ่านไฟล์ หน้าเว็บ หรือ Connector นั้นจริง ถ้าไม่มี Runtime เปลี่ยนเป็น "Agent เดาเอง" ก่อนเขียน แบบคนบอกต้องมีข้อความของ Member ใน Task ที่ Agent อ้างถึง LLM แต่งตัวเลขได้ และตัวเลขในการ์ดดูน่าเชื่อกว่าในข้อความ ป้ายที่มาจึงเป็นส่วนหนึ่งของการ์ด ไม่ใช่ของประดับ

**Question รอคำตอบเหมือน Approval** `ask_choice` และ `ask_form` ทำให้ Turn รอ ทำในนามคนส่งข้อความของ Turn นั้น และมีแค่คนนั้นที่ตอบได้ คำตอบเป็นข้อความที่เซ็นแล้ว และกลายเป็นผลของ tool ถ้าไม่มีใครตอบจนหมดเวลาเท่ากับ Approval ของ Agent นั้น tool คืนว่าไม่มีคำตอบ แล้ว Agent ทำต่อเอง รอบที่ทำงานเองโดยไม่มีคนเฝ้าไม่มี tool นี้ (ADR 0079) Question ที่รออยู่ขึ้นใน Inbox ส่วน "รอคุณ" และส่ง push ไปที่คนที่ตอบได้คนเดียว (ADR 0044) ส่วน Turn ที่ถือล็อกเขียนแล้วรอ Question ยังถือล็อกไว้ เหมือนตอนรอ Approval (ADR 0080)

**หน้าตา** ทุกการ์ดวาดจาก component ของ `shared/ui` (ADR 0072) Question ที่รออยู่ไม่พับเก็บเด็ดขาด และใช้สีส้มซึ่งหมายถึงรอคุณ เมื่อตอบแล้วพับเหลือบรรทัดเดียว เช่น "คุณเลือก: staging" และกดเปิดดูได้ การ์ดแสดงผลไม่พับ และไม่มีปุ่มที่ส่งอะไรกลับไปที่ Agent

**ไม่มี HTML** ไม่มีการ์ดที่ admin เขียนเอง ไม่มีต้นไม้ layout และไม่มี HTML ที่ Agent เขียนเอง Controller เป็นที่ถือกุญแจที่เซ็นคำสั่งของ Member (ADR 0006, 0012) โค้ดที่ LLM เขียนจึงไม่ควรได้รันบนเครื่องนั้น แม้จะอยู่ใน WebView ที่ sandbox ไว้ ชนิดใหม่เพิ่มได้ทีละตัวด้วย ADR และ Protocol แบบ additive

## Considered Options

- **คงไว้แค่ข้อความ Markdown**: ไม่มีงานเพิ่ม แต่คำถามที่มีตัวเลือก ตัวเลข และแผนงานอ่านยากบนมือถือ และ Agent ถามคนได้ทางเดียวคือจบ Turn
- **ต้นไม้ layout แบบ A2UI**: Agent จัดหน้าเองได้ยืดหยุ่น แต่ต้องวาด component ราว 65 ตัวให้ดีบน native และ Agent จะจัดหน้าแตกต่างกันทุกครั้ง ทำให้ Studio direction ที่ต้องเหมือนกันทุกหน้าคุมไม่ได้
- **HTML ใน WebView ที่ sandbox ไว้**: ทำอะไรก็ได้ แต่เป็นโค้ดจาก LLM ที่รันบนเครื่องที่ถือกุญแจ และหน้าตาหลุดจาก theme ของแอป
- **เชื่อป้ายที่มาตามที่ Agent ติดมา**: ง่ายกว่า แต่ป้าย "อ่านมา" ที่ Agent ติดเองไม่ได้บอกอะไรเพิ่ม

## Consequences

- Agent ต้องเลือกเองว่าเมื่อไหร่ควรใช้การ์ด คำอธิบายของ tool จึงต้องบอกตรงๆ เช่น ใช้ `ask_choice` เมื่อตัวเลือกนำไปสู่งานคนละแบบเท่านั้น และใช้ `show_table` เมื่อ list เทียบกันยาก
- กราฟยังไม่มี เพราะกราฟที่ดีบนมือถือใช้เวลาทำ และตัวเลขกับตารางตอบคำถามส่วนใหญ่ได้แล้ว
- event สองชนิดใหม่กับข้อความคำตอบของ Question เพิ่มเข้า Protocol แบบ additive พร้อม test vector
- การตรวจที่มาเทียบได้แค่ว่ามี tool call ที่อ่านแหล่งนั้นจริง ไม่ได้ตรวจว่าตัวเลขตรงกับเนื้อหาที่อ่าน Agent ที่อ่านไฟล์จริงแล้วคัดตัวเลขผิดยังทำได้
- Channel เห็นแค่ `fallback` จนกว่าจะทำปุ่มของแต่ละแชต และตอบ Question ในแชตยังไม่ได้
- การบังคับแผนทำให้ Turn ยาวขึ้นได้อีกไม่เกิน 2 รอบของ LLM และ Agent ที่ตั้งแผนใหญ่เกินจริงจะต้องปิดข้อที่เหลือเป็น "ข้าม" พร้อมเหตุผล ซึ่งคนเห็นในการ์ด
