# Delegation เกิดได้เฉพาะใน Task ของ Team ตามเส้นใน Flow ของทีมนั้น และระบบไม่ส่งงานไปเอง

Member สั่งงานได้สองแบบ คือคุยกับ Agent ตัวเดียว หรือเริ่ม Task กับ Team Delegation เกิดได้เฉพาะใน Task ของ Team ส่วน Task ที่คุยกับ Agent ตัวเดียวไม่มี tool ส่งงานเลย Team แต่ละทีมมีชื่อ มี Flow ของตัวเอง และมี Entry ตัวเดียวที่รับข้อความของ Member Agent ตัวหนึ่งอยู่ได้หลาย Team และในแต่ละ Task ใช้เส้นกับคำแนะนำของ Team ที่ Task นั้นสังกัด เส้นจาก A ไป B หมายถึง A *ส่งงานให้* B ได้ ส่วนจะส่งเมื่อไหร่ Agent เป็นคนตัดสินใจเอง Team ใหม่ยังไม่มีเส้นเลยจนกว่าผู้ใช้จะลาก เหตุผลคือ Agent อ่านข้อมูลจากข้างนอก (เว็บ ไฟล์ issue) ที่อาจมี prompt injection แฝงมา ถ้าปล่อยให้ส่งงานหากันได้อิสระ Agent ที่โดนหลอกแค่ตัวเดียวก็สั่ง Agent ที่มีสิทธิ์สูงกว่าได้ทันที และ Task ที่คุยเดี่ยวต่อให้โดนหลอกก็ส่งงานให้ใครไม่ได้

Flow คือภาพวิธีทำงานของทีมแทนการเขียนเป็นข้อความ ค่าบนผังเป็นได้แค่สองอย่าง คือ **คำแนะนำ** ที่ Runtime ใส่ลงใน prompt ของ Agent ผู้ส่ง (เส้นนี้ใช้ส่งงานแบบไหน และคำอธิบายของ Agent ปลายทาง) หรือ **เพดาน** ที่ Runtime บังคับ ไม่มีค่าไหนที่ทำให้ระบบส่งงานไปเอง Agent เห็นแค่เส้นที่ออกจากตัวเองใน Team ของ Task นั้น ไม่เห็นทั้งผัง เพราะตัดสินใจได้แค่เส้นของตัวเอง และถ้าเห็นทั้งผังจะชวนให้สั่งข้ามชั้นซ้ำกับคำแนะนำบนเส้นของคนอื่น

การตีงานกลับคือการส่งข้อความต่อใน Task ย่อยเดิม และผลของ Task ย่อยกลับไปหา Agent แม่เสมอ เช่น writer ส่งร่างให้ editor ตรวจ ได้ผลว่าไม่ผ่าน แก้แล้วส่งต่อใน Task ย่อยเดิมว่าแก้แล้ว ทั้งวงใช้เส้น writer → editor เส้นเดียว ไม่มีงานไหนต้องใช้เส้นย้อน ผังของ Team จึงห้ามมีวง Agent ส่งงานให้หลายตัวพร้อมกันได้ด้วยการเรียก tool ส่งงานหลายครั้งในคำตอบเดียว และ Turn ของผู้ส่งเปิดรอจนได้ผลครบ Turn จึงยังเริ่มจากข้อความเท่านั้น เมื่อผู้ส่งถือ Turn ไว้รอผล และ Agent ทำได้ทีละ Turn (ADR 0011) เส้นของทุก Team บน Machine เดียวกันรวมกันจึงต้องไม่มีวงด้วย ไม่อย่างนั้นถ้าทีม A มีเส้น editor → writer และทีม B มีเส้น writer → editor สองตัวนี้อาจส่งงานหากันพร้อมกัน แล้วต่างคนต่างรองานที่ต่อคิวอยู่หลัง Turn ของตัวเองไปตลอด

เพดานมีตัวเดียว คือในหนึ่ง Turn ของผู้ส่ง ส่งข้ามเส้นนี้ได้ไม่เกินกี่ครั้ง (ค่าเริ่มต้น 3) นับทั้งการเปิด Task ย่อยใหม่และข้อความต่อใน Task เดิม Agent จึงเลี่ยงด้วยการเปิด Task ย่อยใหม่ไม่ได้ ต้นสายของทุกอย่างคือข้อความของ Member และผังไม่มีวง งานทั้งต้นไม้ที่เกิดจากข้อความเดียวจึงมีขอบเขตเสมอ เมื่อส่งครบ tool ส่งงานจะปฏิเสธ Agent ต้องจบ Turn แล้วส่งสิ่งที่มีกลับไปหาแม่พร้อมบอกว่าค้างอะไร ข่าวไล่ขึ้นไปทีละชั้นจนถึง Entry ทางเดียวกับผลงานปกติ

Member เห็นต้นไม้ของ Task ทั้งหมดและกด Stop ได้ทุกกิ่ง (ADR 0017) แต่พิมพ์ได้แค่ใน Task ของ Entry ถ้าแทรกคุยกับ Agent ข้างล่างตรงๆ Agent แม่จะไม่รู้ว่าแผนเปลี่ยน แล้วอาจตีงานกลับเพราะคิดว่าทำผิด

คนที่ตรวจเส้น เพดาน และ Grant คือ Runtime เพราะ Team อยู่บน Machine เดียว (ADR 0026)

## Considered Options

- **ค่าเริ่มต้นให้ส่งได้หมด**: ตอนเริ่มใช้สะดวกกว่า แต่เปิดช่องให้การโจมตีข้างต้น
- **Flow ชุดเดียวทั้ง Workspace แล้วเปิดโหมดทีมที่ Task**: ไม่ต้องมี Team เป็นของแยก แต่ผังเดียวรกขึ้นทุกครั้งที่มีงานแบบใหม่ และ Agent ตัวเดียวที่ใช้ต่างกันในแต่ละงาน เช่น reviewer ตรวจโค้ดกับตรวจบทความ ใส่คำแนะนำสองแบบบนเส้นเดียวไม่ได้
- **เข้า Team ทาง Agent ตัวไหนก็ได้**: ยืดหยุ่นกว่า แต่คำแนะนำบนเส้นต้องใช้ได้ไม่ว่างานจะเริ่มจากตรงไหน และอ่านผังไม่ออกว่างานเข้ามาทางไหน
- **Flow เป็นลำดับขั้นตายตัวแบบ n8n หรือป้าย "ส่งต่อเสมอ" บนเส้น**: คาดเดาได้ แต่ต้องมี engine ตัดสินว่างาน "จบ" แล้วคืออะไร และ Stop คิว กับ Approval ต้องคิดใหม่ทั้งหมด ลำดับที่ห้ามพลาดใช้ Allowlist กับ Approval ของ Agent ปลายทางคุมแทน
- **ต้องอนุมัติก่อนข้ามเส้น**: การข้ามเส้นเองไม่ได้ทำอะไรอันตราย สิ่งที่อันตรายคือสิ่งที่ปลายทางลงมือทำ ซึ่ง Allowlist กับ Approval คุมอยู่แล้ว คนจะต้องกดสองครั้งต่องานเดียว
- **ให้มีวง แล้วคุมด้วยเพดานความลึก**: วงไม่ได้ทำให้ทีมทำอะไรได้มากขึ้น เพราะตีกลับและถามกลับทำได้ด้วยการคุยต่อใน Task ย่อยเดิม
- **ห้ามวงแค่ในทีมเดียว แล้วให้ Runtime ตรวจตอนส่งงานว่าจะเกิดการรอกันเป็นวงไหม**: Team อิสระจากกันได้มากกว่า แต่จะพังเฉพาะจังหวะที่สองทีมบังเอิญทำงานชนกัน ทำให้หาสาเหตุยาก ถ้าผู้ใช้เจอข้อจำกัดของการห้ามวงทั้งเครื่องบ่อย ค่อยเปลี่ยนมาใช้ทางนี้
- **ตั้งเวลาหมดอายุให้การรอผลของ Delegation**: แค่เปลี่ยนจากค้างตลอดไปเป็นค้างนาน แล้วได้ผลที่อธิบายไม่ได้กลับมา
- **ส่งครบเพดานแล้วเปิด Approval ถามคนว่าให้ส่งอีกรอบไหม**: Approval มีความหมายเดียวคือ Agent จะทำสิ่งที่ไม่อยู่ใน Allowlist และไปหาคนที่มี Approve ซึ่งอาจไม่ใช่คนที่สั่งงาน (ADR 0010)
- **tool ส่งงานตอบทันที แล้วให้ผลปลุก Agent แม่ขึ้นมาทำ Turn ใหม่**: ระหว่างรอ Agent แม่ว่าง แต่จะมี Turn ที่เริ่มจากผลของ Task ย่อย เพดานต่อ Turn จะรีเซ็ตทุกครั้งที่ผลกลับมา และต้องจำข้าม Turn ว่ายังรอใครอยู่
- **ให้ Member แทรกข้อความใน Task ย่อย**: แก้ทางได้เร็วกว่า แต่บทสนทนาหลักของทีมแตกเป็นหลายเส้น

## Consequences

- ระหว่างที่ทีมทำงาน Entry ไม่ว่าง (ADR 0011) ข้อความใหม่ของ Member ต่อคิวรอ Member จึงทำได้แค่ดูกับกด Stop ถ้างานยาวเป็นชั่วโมงจะรู้สึกได้
- คำแนะนำบนเส้นรับประกันไม่ได้ว่า Agent จะทำตามทุกครั้ง Controller จึงต้องแสดงคำแนะนำกับเพดานให้ต่างกัน และแสดงต้นไม้ของ Task จริงให้เทียบกับผังได้
- Team บน Machine เดียวกันไม่อิสระจากกันเต็มที่ ถ้าทีม A มีเส้น editor → writer ทีม B จะลากเส้น writer → editor ไม่ได้ Controller ต้องบอกว่าเส้นที่กำลังลากชนกับเส้นไหนของทีมไหน
- เรื่องที่ทุกตัวในทีมต้องรู้ เช่น writer ส่งงานให้ editor ตรวจก่อนส่งกลับเสมอ ต้องเขียนไว้ในคำอธิบายของ Agent เพราะ Agent ข้างบนไม่เห็นเส้นของ Agent ข้างล่าง
