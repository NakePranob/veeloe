# Runtime แบ่งเป็น supervisor หนึ่งตัวกับ worker หนึ่งโปรเซสต่อ Agent

Bun รันลูปหลักแค่ลูปเดียว ถ้าทุก Agent อยู่ในโปรเซสเดียวกัน แล้ว Agent ตัวหนึ่งติดงานหนักที่ไม่ได้แบ่งเวลาให้ตัวอื่น เช่น grep ไล่ repo ใหญ่ หรือ regex ที่วนไม่จบ Agent ทุกตัวบนเครื่องนั้นจะค้างหมด รวมถึงการเชื่อมต่อกับ Hub ด้วย เราจึงแบ่ง Runtime เป็นสองส่วน **supervisor** ทำ hub-link, trust, cli และ updater และเก็บกุญแจที่ไว้ใจ เลขกันส่งซ้ำ และรายชื่อ Agent ไว้ในไฟล์ของตัวเอง ส่วน **worker ของแต่ละ Agent** ทำ scheduler, harness, tools และ tasks และมีไฟล์ bun:sqlite ของตัวเอง เพราะ Task เป็นของ Agent ตัวเดียวอยู่แล้ว ข้อนี้เข้ากับ ADR 0011 พอดี คือ 1 Agent = 1 คิว = 1 โปรเซส supervisor ตรวจลายเซ็นทุกครั้งก่อนส่งงานต่อให้ worker และสั่ง restart worker ที่พังได้ ทุกโปรเซสใช้ OS user เดียวกัน

Runtime ออกมาเป็น binary ไฟล์เดียวที่รันได้สองโหมด สั่ง `veeloe` เฉยๆ จะเป็น supervisor ส่วน supervisor เปิด worker ด้วยคำสั่ง `veeloe worker --agent <id>` เราจึงแจกจ่าย เซ็น และอัปเดต (ADR 0009) ทีละไฟล์เดียว และ supervisor กับ worker เป็นเวอร์ชันเดียวกันเสมอ ไม่มีกรณีที่อัปเดตได้ครึ่งเดียวแล้วสองตัวคนละเวอร์ชัน

## Considered Options

- **โปรเซสเดียว**: ง่ายที่สุด แต่ Agent ตัวหนึ่งค้างแล้วตัวอื่นค้างตาม
- **แยก OS user ต่อ Agent ตั้งแต่แรก**: Agent อ่านไฟล์ของกันและกันไม่ได้จริงในระดับ OS แต่ตอนติดตั้งต้องใช้สิทธิ์ root หรือ admin และ Agent จะใช้ไฟล์ใน home ของเจ้าของเครื่องได้ยาก
- **Bun Worker thread**: ไม่ได้ช่วยเรื่องความปลอดภัย เพราะใช้สิทธิ์ OS ชุดเดียวกัน แต่ได้ความซับซ้อนของการส่งข้อความระหว่าง thread มาแทน

## Consequences

- Agent ที่รันหลาย Turn พร้อมกันในคนละ Worktree (ADR 0047) หรือตอบ Ask ไปพร้อมกับงาน (ADR 0046) มี worker หลายโปรเซส หนึ่งตัวต่อ Turn ที่รันอยู่ แต่ละตัวมี sandbox ตามที่เขียนของ Turn นั้น
- harness ใน worker ส่งคำขอไป LLM ผ่าน proxy ใน supervisor ซึ่งถือ key ของ Provider (ADR 0042)

- การแยกโปรเซสไม่ได้เพิ่มความปลอดภัยระหว่าง Agent ด้วยกัน เพราะยังใช้ OS user คนเดียวกัน ตัวกันจริงยังเป็น sandbox (ADR 0008) ถ้าวันหลังจะแยก OS user ก็ทำได้โดยไม่ต้องรื้อโครงสร้าง
- ใช้ RAM ราว 30-50 MB ต่อ Agent
