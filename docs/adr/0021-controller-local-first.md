# Controller เป็นแบบ local-first: ข้อมูลทุกอย่างลง SQLite บนเครื่องก่อน

Controller ต้องรวม event log จาก Runtime หลายเครื่อง (ADR 0018) กับ metadata จาก Hub ต้องแสดงสิ่งที่เคยเห็นได้แม้ไม่มีสัญญาณ (ADR 0005) และต้องคำนวณ Mood จาก event ข้อมูลทุกอย่างที่ได้รับจึงเขียนลง expo-sqlite บนเครื่องก่อนเสมอ ทั้ง event ของ Task และ metadata ของ Machine, Agent และ Flow หน้าจออ่านจาก database แบบ live query ส่วนการ sync แยกเป็นอีกตัวหนึ่ง ทำหน้าที่ขอ "event หลังเลข N" ของแต่ละ Task หน้าจอกับการ sync จึงไม่ผูกกัน และแอปมีทางเดินข้อมูลแค่ทางเดียว การนำทางใช้ Expo Router เพื่อให้แตะ push แล้วเปิดตรงไปที่หน้า Approval ได้ และมี URL บนเว็บ

## Considered Options

- **เก็บในหน่วยความจำ (Zustand) แล้ว persist เป็น snapshot**: เริ่มง่ายกว่า แต่ snapshot จะใหญ่และช้าเมื่อ event เยอะ ถ้าแอปปิดก่อน persist ก็ตกหล่น และต้องเขียนโค้ดรวม event จากหลายที่เอง
- **TanStack Query ดึงตอนเปิดหน้า**: เหมาะกับข้อมูลแบบ REST แต่ไม่เหมาะกับ event ที่ไหลเข้ามาตลอด และไม่มี cache ที่ใช้ตอนออฟไลน์ได้จริง

## Consequences

- spike กับ Expo SDK 58 และ expo-sqlite 58.0.13 ยืนยันว่าบนเว็บใช้ได้ทั้ง Chromium, WebKit และ Firefox ข้อมูลยังอยู่หลัง reload และหลังปิดเปิดเบราว์เซอร์ ใส่ 10,000 แถวแบบ batch ใช้เวลา 74-273 ms และ query 100 แถวล่าสุดใช้ 0.3-2 ms ข้างในใช้ wa-sqlite ที่รันใน worker และเก็บไฟล์ไว้ใน OPFS
- บนเว็บต้องใช้ API แบบ async ของ expo-sqlite และเขียน hook สำหรับ live query เอง ไม่ใช้ drizzle บนเว็บ เพราะ drizzle ใช้ API แบบ sync ซึ่งต้องมี SharedArrayBuffer และต้องตั้ง header แยก origin ส่วน Safari ยอมแค่ `COEP: require-corp` ซึ่งบังคับให้ทรัพยากรจากโดเมนอื่นทุกชิ้นต้องส่ง CORP หรือ CORS มาด้วย ถ้าใช้ API แบบ async ก็ไม่ต้องตั้ง header พิเศษบน hosting เลย นอกจากนี้ Metro ต้องรู้จักไฟล์ `.wasm` และต้องเสิร์ฟเป็น `application/wasm` ซึ่งทำให้ bundle ใหญ่ขึ้นราว 350 KB หลังบีบอัด
- change event ยิงทีละแถวและยิงก่อน commit ชั้น db ใน shared จึงต้องรวมเป็นการแจ้งครั้งเดียวต่อ commit ในรูป "Task X อยู่ที่เลข N แล้ว" ถ้าไม่รวม การ sync 1,000 event ขณะที่หน้าจอเปิดอยู่จะช้าลงจากราว 10 ms เป็น 1.2-4.4 วินาที
- บนเว็บ SQLite เป็นแค่ cache ที่สร้างใหม่ได้เสมอ เพราะเบราว์เซอร์ลบข้อมูลเองได้ (`storage.persisted()` ได้ false ทุกเบราว์เซอร์ และ Safari ลบข้อมูลของเว็บที่ไม่ได้ติดตั้งหลัง 7 วัน) จึงต้องเรียก `navigator.storage.persist()` และ sync ใหม่จากเลข 0 ได้ทุกเมื่อ ส่วนโหมดส่วนตัวของ WebKit เปิด database ไม่ได้เลย ให้ใช้ database ในหน่วยความจำแล้ว sync ใหม่ทั้งหมดแทน
- บนเว็บไม่มี full-text search
- บนเว็บเปิด database ได้ทีละแท็บเดียวในทุกเบราว์เซอร์ แท็บที่สองจึงแสดงว่า "Veeloe เปิดอยู่ในอีกแท็บ" พร้อมปุ่ม "ใช้ที่นี่" แบบเดียวกับ WhatsApp Web พอกดแล้ว แท็บเดิมจะปล่อย database ให้ แต่ละแท็บรู้ว่าใครถือ database อยู่ผ่าน Web Locks กับ BroadcastChannel ถ้าวันหลังต้องใช้หลายแท็บพร้อมกัน ให้ทำแท็บหลักที่ถือ database แล้วให้แท็บอื่นขอข้อมูลผ่านแท็บนั้น ซึ่งประเมินว่าใช้เวลา 1-2 สัปดาห์
- cache บนเครื่องโตขึ้นเรื่อยๆ วันหลังต้องมีกติกาว่าจะเก็บ Task เก่าไว้บนเครื่องนานแค่ไหน
