# Project มี repo ได้หลายอัน และ Task ที่ติ๊ก Worktree ทำงานขนานกันได้

ทุก Task ของ Project ผ่าน Entry (ADR 0045) ถ้า Agent ทำได้ทีละ Turn ตามที่ ADR 0011 วางไว้ ห้องต่างๆ จะรอกันที่ Entry ทำงานขนานไม่ได้เลย ส่วนเหตุผลที่ ADR 0011 ให้ทำทีละ Turn คือสองงานจะเขียนไฟล์ทับกัน เราจึงย้ายกฎคนเขียนคนเดียวจากต่อ Agent ไปเป็นต่อที่เขียน Project มี repo ได้หลายอัน อยู่ที่ `<VEELOE_HOME>/projects/<id>/repos/<ชื่อ>/` และพนักงานเขียนได้ระหว่างทำ Task ของ Project ตอนเปิด Task ติ๊ก Worktree ได้ Task นั้นจะได้สำเนาของทุก repo ใน branch ชื่อเดียวกัน งานที่แก้หลาย repo เช่น API กับหน้าจอจึงอยู่ใน Task เดียว worktree หนึ่งของ repo หนึ่งมีคนเขียนได้ทีละหนึ่ง Turn Task ที่ไม่ติ๊กใช้ checkout หลักร่วมกันทีละหนึ่ง Turn และ Agent ทั้ง Entry และพนักงานรันหลาย Turn พร้อมกันได้ ถ้าแต่ละ Turn อยู่คนละ worktree ระหว่างนั้น Workdir ของ Agent รวมถึง `MEMORY.md` อ่านได้อย่างเดียว ไม่อย่างนั้นหลาย Turn ที่รันพร้อมกันจะเขียน Workdir ทับกัน ผลงานออกมาเป็น branch ที่รวมเข้า main ด้วย PR ผ่าน Connector หรือสั่งให้ Entry merge และ Member เป็นคนลบ worktree เมื่องานเสร็จ

Project ที่เป็นงานไม่ใช่โค้ด เช่น เอกสาร research หรือดีไซน์ ให้ Runtime สร้าง repo ไฟล์งานให้เองบนเครื่องโดยไม่ต้องมี remote แอปพูดเป็น "สำเนาของห้อง" "รวมงาน" และ "ย้อนไปเวอร์ชันก่อน" ส่วนคำสั่ง git ทั้งหมด Agent เป็นคนรัน Project ที่ไม่มีผลงานเป็นไฟล์ เช่น support, ops หรืองานหลังบ้านที่จบในระบบอื่นผ่าน Connector ไม่ต้องมี repo แต่ละ Task ได้โฟลเดอร์ว่างของตัวเองที่ `<VEELOE_HOME>/projects/<id>/tasks/<task-id>/` แทน ใช้กฎเดียวกับ worktree และไม่ต้องรวมงานกลับ ตอนสร้าง Project เลือกแม่แบบได้ เช่น โค้ด เอกสารกับ research ดีไซน์กับสื่อ หรืองานผ่านระบบอื่น แม่แบบเป็นแค่ค่าตั้งต้นในแอป เช่น มี repo หรือไม่ ติ๊ก worktree ไว้ก่อนหรือไม่ และ Skill ที่แนะนำ ไม่ได้เป็นระบบแยกกัน

ไฟล์ binary อย่าง `.docx` หรือรูปรวมด้วย git ไม่ได้ เราจัดการด้วยงานเล็กๆ ไม่มีระบบล็อกไฟล์ งานเอกสารเก็บต้นฉบับเป็นข้อความ เช่น Markdown, CSV, Marp หรือ SVG แล้ว export เป็น docx, pdf หรือ pptx ด้วย Skill ไฟล์ที่ export แก้ตรงไม่ได้ แม่แบบดีไซน์กับสื่อปิด worktree ไว้ก่อนจึงไม่ชนกัน ถ้ายังชนกันในกรณีอื่น เช่น repo โค้ดที่มีรูปปน ให้เก็บไว้ทั้งสองเวอร์ชันแล้วให้คนเลือก หรือให้ Agent อ่านทั้งสองแล้วรวมใหม่ ความต่างของไฟล์ binary แสดงด้วย textconv ของ git เช่น pandoc สำหรับ `.docx` และไฟล์ที่ใหญ่เกินเพดานใช้ Git LFS หรือเก็บไว้ใน Library

## Considered Options

- **Project มี repo แต่ทุกอย่างยังทำทีละ Turn ต่อ Agent**: ไม่ต้องแก้ ADR 0011 กับ 0020 แต่ทุกห้องรอคิวกันที่ Entry
- **โหมด worktree ที่ตั้งต่อ Agent**: เคยคิดก่อนมี Project แต่ Agent ที่ทำงานร่วมกันบน repo เดียวต้องมีที่รวม repo อยู่ดี ซึ่งก็คือ Project
- **worktree ต่อ Task ย่อยของพนักงาน แล้ว Entry merge**: ขนานได้มากที่สุดแม้ใน Task เดียว แต่ merge conflict เกิดบ่อย และ Entry ต้อง merge ทุกครั้ง
- **ล็อกไฟล์ binary ข้าม worktree แบบ Git LFS**: กันการทำงานซ้ำเสีย แต่ต้องมีตารางล็อก ล็อกค้าง และตรวจการเขียนผ่าน bash ทั้งที่ไฟล์ binary ส่วนใหญ่อยู่ในงานดีไซน์ที่ปิด worktree อยู่แล้ว
- **ประเภทของ Project เป็นระบบแยกกัน**: ออกแบบพอดีกับแต่ละงาน แต่มีโค้ดหลายชุด และงานจริงมักปนกัน

## Consequences

- ADR 0011 เปลี่ยนจาก "Workdir หนึ่งมีคนเขียนคนเดียว" เป็น "Workdir หรือ worktree หนึ่งมีคนเขียนคนเดียว" และ ADR 0020 เปลี่ยนจาก worker หนึ่งตัวต่อ Agent เป็นหนึ่งตัวต่อ Turn ที่รันอยู่
- ทรัพยากรชนกันได้ `node_modules` ซ้ำทุก worktree, dev server แย่ง port และ test ใช้ database ในเครื่องตัวเดียวกัน Runtime ควรตั้ง `PORT` ไม่ซ้ำกันต่อ worktree และแอปต้องเตือน
- merge conflict ตอนรวม branch ยังเกิดได้ และงานขนานใช้ Budget เร็วขึ้น
- Agent จด Memory ได้เฉพาะตอนทำงานที่ไม่ได้อยู่ใน worktree ถ้าเจอปัญหาจริงค่อยให้ supervisor ต่อคิวการเขียน Memory
- Character ต้องแสดงได้ว่า Agent ตัวเดียวกำลังทำหลายงาน
- งานที่ไม่มี repo ซึ่งขนานกันยังชนกันในระบบภายนอกได้ เช่น สองห้องแก้ ticket ใบเดียวกัน Entry ต้องกระจายงานไม่ให้ซ้อนกัน
