# แบ่งงานเป็นห้า phase และ v0.1 คือ MVP ที่ Owner คนเดียวสั่ง Agent บนเครื่องตัวเองจากมือถือ

> **ADR 0064 เพิ่มเติม** Team มาพร้อม Project ใน v0.4

ADR ตั้งแต่ 0001 ถึง 0047 ออกแบบไว้มากกว่าที่ต้องสร้างก่อนเปิดให้คนใช้ ถ้าไม่ตัดขอบเขต ticket ชุดใหม่จะไม่มีลำดับ และ v0.1 จะไม่มีวันเสร็จ เราจึงแบ่งตามลำดับที่เรื่องหนึ่งต้องพึ่งอีกเรื่อง v0.1 ต้องพิสูจน์แค่ว่าสั่ง Agent บนเครื่องตัวเองจากมือถือได้อย่างปลอดภัย และไม่เสียเงินเกินที่คิด ส่วนที่เหลือเพิ่มทีหลังได้แบบ additive (ADR 0023) ก่อนมี E2E Hub ของเราอ่านเนื้อหาได้ (ADR 0005) v0.1 และ v0.2 จึงมีแค่เจ้าของระบบใช้ และเปิดให้คนอื่นใช้ได้ตั้งแต่จบ v0.3

1. **v0.1 (MVP)**: Hub ที่ส่งต่อข้อความ, Pairing, Linking เครื่องที่สองด้วย QR และการถอนกุญแจ (ADR 0031), สร้าง Agent และคุยใน Task, Attachment (ADR 0050), Approval, Stop, Allowlist, sandbox บน macOS และ Linux กับ Egress รายชื่อเดียวทั้ง Machine (ADR 0008), Provider ที่ตั้งบน Machine พร้อม proxy และ Budget (ADR 0042, 0043), Memory กับ compaction (ADR 0036, 0041), push ของ Approval, Turn ที่เสร็จ และ Budget (ADR 0044), Controller แบบ local-first พร้อม Character, log และสถานะของ Machine (ADR 0052) v0.1 มี Member คนเดียวคือ Owner
2. **v0.2 Agent ทำงานเองได้มากขึ้น**: Schedule, Idle Work, Watch, เส้นร้อย Task (ADR 0061), `web_fetch` และการค้นเว็บ, Skill, Connector และ Library
3. **v0.3 องค์กรและเปิดให้คนอื่นใช้**: เริ่มจาก E2E (ADR 0063) แล้วตามด้วย Egress แยกต่อ Agent (ADR 0029), Invitation ที่แนบ Grant ได้, Owner หลายคน, Grant ให้ Member คนอื่น, การเลือกผู้รับจาก Grant, ขอบเขตการอ่านตามคนสั่งพร้อมการเปิด worker ใหม่ (ADR 0059), กฎการเปิดดู Task กับค่าการค้น Task (ADR 0060), ยอดใช้ต่อ Member ต่อเดือน, บัญชีของ Member, Linking ด้วย login และการกู้บัญชีด้วย email (ADR 0013) และการย้าย Machine จากนั้นเป็นชุดเปิดตัว ได้แก่ Runtime ที่อัปเดตตัวเองแบบเซ็น (ADR 0009), `veeloe backup` กับ `restore` (ADR 0051), Demo Workspace กับการลบบัญชี (ADR 0024) และการเก็บเงินพร้อมโควตาตอน Pairing (ADR 0001) ถ้า phase นี้ใหญ่เกินไป แยกชุดเปิดตัวออกเป็น phase ของตัวเองได้
4. **v0.4 Project**: Project, Ask ทั้งใน Project และนอก Project, Mention, Worktree และ Agent ที่รันหลาย Turn พร้อมกัน ไว้หลังสุดของงานแกน เพราะเปลี่ยน Runtime จาก worker ต่อ Agent เป็น worker ต่อ Turn (ADR 0020, 0047)
5. **v0.5 Channel**: Telegram และ `/claim` (ADR 0028, 0058) Channel ไม่ต้องรอ Project ถ้าต้องการเร็วกว่านี้ ยกไปไว้หลัง v0.3 ได้ ถ้าจะเอามาก่อน v0.3 ต้องเอา Egress แยกต่อ Agent มาด้วย (ADR 0029)

marketplace ของ Blueprint (ADR 0049) มาหลัง v0.3

## Considered Options

- **v0.1 มี Schedule หรือ Channel ด้วย**: จุดขายชัดกว่าตั้งแต่วันแรก แต่ทั้งสองอย่างทำงานโดยไม่มีคนกด จึงต้องมี Budget, sandbox และ Approval ที่นิ่งแล้วก่อน
- **ทำองค์กรก่อน Agent ทำงานเอง**: ขายให้บริษัทได้เร็วกว่า แต่ต้องรอ E2E ซึ่งเป็นงานใหญ่ ในขณะที่ v0.2 ใช้ได้กับ Owner คนเดียว
- **ทำ Project ก่อนองค์กร**: Project ใช้กับ Owner คนเดียวได้ แต่เปลี่ยนโครง Runtime มากที่สุด ถ้าทำก่อน งานของ v0.2 และ v0.3 ต้องสร้างบนโครงที่ยังไม่นิ่ง
- **ทำ E2E ใน v0.1 แล้วเปิดให้คนอื่นใช้ได้เร็วขึ้น**: มีผู้ใช้จริงเร็วกว่า แต่ v0.1 ใหญ่ขึ้นมาก และต้องออกแบบการเข้ารหัสบนระบบที่ยังไม่นิ่ง
- **push แค่ Approval ใน v0.1**: งานน้อยกว่าเล็กน้อย แต่คนสั่งงานแล้ววางมือถือจะไม่รู้ว่างานเสร็จหรือ Budget ใกล้หมด

## Consequences

- ADR ที่เขียนว่าอะไรไม่อยู่ใน v0.1 ยังถูกอยู่ ADR นี้เพิ่มแค่ว่าแต่ละเรื่องอยู่ phase ไหน
- ข้อมูลต้องเตรียมไว้รองรับ phase ถัดไปตั้งแต่ v0.1 เช่น เก็บ Owner และ Member เป็นรายชื่อ (ADR 0010, 0031) รายชื่อผู้รับในหัวซอง (ADR 0034) และยอด token ที่ระบุ Member (ADR 0043) แม้จะมีคนเดียว
- ticket ชุดใหม่ (`/to-tickets`) แบ่งตาม phase นี้
- ก่อนจบ v0.3 ไม่มีคนนอกใช้ เจ้าของระบบจึงติดตั้ง Runtime รุ่นใหม่เอง และแอปยังไม่ขึ้น store ถ้าข้อมูลหายก็เสียแค่ของเจ้าของระบบ
- v0.1 ยังไม่มี email ถ้า Controller เครื่องเดียวที่มีหาย หรือเปลี่ยน biometric จนกุญแจใช้ไม่ได้ (ADR 0012) ต้องทำ Pairing ใหม่ที่หน้าเครื่องจากศูนย์ (ADR 0031) แอปจึงต้องเตือนให้ Link เครื่องที่สอง
- ปัญหาที่ Hub กักคำสั่งถอนได้ต้องตอบก่อนเริ่ม E2E (ADR 0063) และ E2E ต้องเสร็จก่อนมี Member คนที่สอง
- ระหว่าง v0.2 ถึง v0.3 ยังไม่มี Ask นอก Project คนที่เจอ Agent ทำ Idle Work อยู่ต้องรอไม่เกินเพดานเวลาของงาน หรือกด Stop (ADR 0056)
