# Delegation ส่งงานด้วยช่องที่กำหนด และ Member แทรกความเห็นใน Task ย่อยได้โดยข้อความไปถึง Entry

> แก้ ADR 0045 บางส่วน ตามที่เขียนไว้ในหัวของ ADR นั้น

Delegation ตาม ADR 0045 ให้ Entry ส่งงานเป็นข้อความเปล่า พนักงานจึงต้องเดาว่างานจบเมื่อไหร่และต้องส่งอะไรกลับ แล้วตอบอย่างมั่นใจในสิ่งที่ Entry ไม่ได้ขอ ADR เดียวกันยังห้าม Member พิมพ์ใน Task ย่อย เพราะถ้าคุยกับพนักงานตรงๆ Entry จะไม่รู้ว่าแผนเปลี่ยน ผลคือคนที่เห็นพนักงานกำลังทำผิดทางต้องกลับไปพิมพ์ใน Task ของ Entry แล้วอธิบายเองว่าหมายถึงงานย่อยไหน OpenBot (nightly-labs/openbot) แก้เรื่องแรกด้วยการส่งงานใน channel พร้อมช่อง task และ expectedResult ส่วนข้อความของคนใน channel ไปถึง lead หรือสมาชิกที่ถูกเรียกชื่อ ไม่ได้พิมพ์ในงานย่อย เราจึงคิดทางของเราเองสำหรับเรื่องที่สอง (เจ้าของตัดสิน 2026-11-27)

**ช่องของ Delegation** tool ส่งงานมีสามช่อง ได้แก่ `task` คืองานที่ต้องทำ (ต้องมี), `constraints` คือข้อจำกัด เช่น ห้ามแตะไฟล์ไหน หรือต้องเสร็จภายในเท่าไหร่ (ใส่หรือไม่ใส่ก็ได้) และ `wanted_back` คือสิ่งที่ต้องส่งกลับ เช่น รายชื่อไฟล์ที่แก้พร้อมเหตุผล (ต้องมี) Runtime ปฏิเสธการส่งที่ขาดช่องที่ต้องมี และสร้างข้อความแรกของ Task ย่อยจากช่องเหล่านี้ในรูปแบบเดียวกันทุกครั้ง ข้อความต่อใน Task ย่อยเดิม เช่น การตีงานกลับ ยังเป็นข้อความเปล่าได้

**ข้อความแทรกไปถึง Entry** Member ที่มี Use ของ Project พิมพ์ใน Task ย่อยได้ ช่องพิมพ์บอกว่า "ส่งถึง <Entry>" ข้อความนั้นเข้าคิวเป็นข้อความของ Member ใน Task ของ Entry ตามปกติ (ADR 0080) โดยแนบว่าเกี่ยวกับ Task ย่อยไหน และแสดงใน Task ย่อยด้วยว่าส่งถึง Entry แล้ว พนักงานไม่เห็นข้อความนี้ Entry เป็นคนตัดสินว่าจะส่งต่อหรือไม่ และการส่งต่อนับเป็น Delegation ในเพดานของ Turn นั้น Turn ที่เกิดจากข้อความนี้ทำในนามคนพิมพ์ (ADR 0010)

## Considered Options

- **คงข้อความเปล่า**: Entry เขียนอะไรก็ได้ แต่พนักงานต้องเดาว่าต้องส่งอะไรกลับ และงานที่ไม่บอกว่าเสร็จเมื่อไหร่ก็ไม่จบ
- **ให้ Member คุยกับพนักงานตรงๆ ใน Task ย่อย**: เร็วกว่า แต่ Entry ไม่รู้ว่าแผนเปลี่ยน แล้วอาจตีงานกลับเพราะคิดว่าพนักงานทำผิด ตามที่ ADR 0003 และ 0045 ปฏิเสธไว้
- **คงไว้ว่าพิมพ์ได้แค่ใน Task ของ Entry**: ไม่มีงานเพิ่ม แต่คนต้องอธิบายเองว่าหมายถึงงานย่อยไหน

## Consequences

- ข้อความแทรกไปถึงพนักงานช้ากว่าพิมพ์ตรง เพราะต้องรอ Entry อ่านแล้วส่งต่อ ถ้า Entry กำลังทำ Turn อื่นใน Task เดียวกัน ข้อความต้องรอคิว
- Stop ใน Task ย่อยยังหยุดพนักงานได้ทันทีเหมือนเดิม (ADR 0017) ข้อความแทรกจึงไม่ใช่ทางเดียวที่จะหยุดงานผิดทาง
- `wanted_back` ช่วยให้พนักงานรู้ว่าต้องส่งอะไร แต่ Runtime ไม่ได้ตรวจว่าสิ่งที่ส่งกลับตรงกับที่ขอ Entry เป็นคนตรวจ
