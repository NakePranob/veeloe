# Egress แยกต่อ Agent ไม่มีรายชื่อกลางของ Machine

ADR 0008 ให้ Egress ตั้งต่อ Machine เพราะ sandbox-runtime มี proxy ตัวเดียวใน supervisor และแยกรายชื่อต่อ Agent ไว้แค่เพื่อบันทึกว่าใครเรียก ความเสี่ยงที่เหลือรับได้เพราะคนที่สั่ง Agent มีแค่ Member ที่ไว้ใจกัน และ token ของแต่ละ Agent อยู่ใน Workdir ที่ sandbox กันไว้ เงื่อนไขนี้ไม่จริงอีกสองกรณี กรณีแรกคือมี Member หลายคนที่ได้ Grant คนละ Agent (ADR 0010) ถ้า Agent B ต้องเรียก `api.internal.company` ที่ไม่ใช้ token เพราะอยู่ในเครือข่ายภายใน Member ที่มี Use แค่ที่ Agent A บนเครื่องเดียวกันก็สั่ง A ให้เรียกโดเมนนั้นได้ ซึ่งเป็น confused deputy แบบที่ ADR 0010 ปิดไว้ แต่มาทางเน็ต กรณีที่สองคือ Channel (ADR 0028) ที่คนนอกสั่ง Agent ได้ เราจึงให้ Agent แต่ละตัวมี Egress ของตัวเอง และไม่มีรายชื่อกลางของ Machine ให้ supervisor ทำ proxy ต่อ Agent ตามทางที่ ADR 0008 เผื่อไว้ การแก้ Egress ต้องมี Manage ที่ Agent ตัวนั้น เหมือนการแก้ค่าอื่นของ Agent ส่วนความลำบากตอนต้องพิมพ์โดเมนซ้ำทุก Agent ให้แอปเสนอคัดลอก Egress จาก Agent ตัวอื่นบนเครื่องเดียวกันตอนสร้าง Agent ซึ่งเป็นแค่ทางลัดในแอป ไม่ได้มีรายชื่อชุดที่สอง

v0.1 ยังใช้รายชื่อเดียวทั้ง Machine ตามที่ ADR 0008 ทำไว้ เพราะมี Owner คนเดียวและยังไม่มี Channel จึงยังไม่มีใครใช้สิทธิ์ข้าม Agent ได้ ระบบเปลี่ยนเป็นแยกต่อ Agent เมื่อมีอย่างใดอย่างหนึ่งก่อน คือ Member คนที่สองผ่าน Invitation (ADR 0031) หรือ Channel ตอนเปลี่ยนให้คัดลอกรายชื่อของ Machine ไปเป็นค่าเริ่มต้นของ Agent ทุกตัว จึงไม่มี Agent ตัวไหนออกไปที่เดิมไม่ได้

Egress ของ Agent ตั้งให้ออกได้ทั้งเน็ตสาธารณะก็ได้ สำหรับงาน research ที่ต้องดาวน์โหลดไฟล์หรือเรียก API ที่บอกล่วงหน้าไม่ได้ว่าเป็นโดเมนไหน แต่ "ทั้งเน็ต" ไม่รวมที่อยู่ภายใน ได้แก่ loopback, เครือข่ายส่วนตัว และ link-local ซึ่งรวม `169.254.169.254` ที่ cloud ใช้แจก credential ให้เครื่อง proxy ตรวจที่อยู่ที่โดเมนชี้ไปก่อนต่อ และระหว่างที่ตั้งแบบนี้ Agent อ่านไฟล์ได้แค่ใน Workdir ของตัวเองกับ Library ที่ได้สิทธิ์ (ADR 0037) เพราะหน้าเว็บไหนก็ฝังคำสั่งได้ คนนอกจึงสั่ง Agent ได้ทางอ้อมแบบเดียวกับ Channel

## Considered Options

- **รายชื่อของ Machine รวมกับรายชื่อของ Agent**: โดเมนที่ทุกตัวต้องใช้ใส่ไว้ที่เครื่องครั้งเดียว แต่ทุกอย่างที่อยู่ในรายชื่อของเครื่อง Agent ทุกตัวออกไปได้ รวมถึง Agent ที่มี Channel และ Agent ที่ Member ไม่มี Grant ช่องเดิมจึงกลับมาทันทีที่มีคนใส่โดเมนภายในไว้ที่ระดับเครื่อง
- **รายชื่อของ Machine เป็นเพดาน และ Agent เลือกได้เฉพาะในนั้น**: ฝ่าย IT ขององค์กรคุมได้ว่าเครื่องนี้ออกไปได้แค่ไหน แต่ต้องมีสิทธิ์ระดับ Machine ซึ่งยังไม่มี และทุกโดเมนใหม่อาจต้องแก้สองที่ เพิ่มทีหลังได้โดยไม่ทำให้อะไรพัง ด้วยการตั้งเพดานเริ่มต้นเป็นรายชื่อรวมของทุก Agent บนเครื่อง
- **แยกต่อ Agent ตั้งแต่ v0.1**: ไม่ต้องเปลี่ยนรูปแบบข้อมูลทีหลัง แต่ต้องเขียน proxy ต่อ Agent ซึ่งเป็นโค้ดด้านความปลอดภัยที่ spike ใน ADR 0008 ยังไม่เคยทดสอบ ทั้งที่ v0.1 ยังไม่มีใครได้ประโยชน์
- **ทั้งเน็ตรวมที่อยู่ภายในด้วย**: ตั้งง่ายกว่า แต่เปิดวิกิภายใน แดชบอร์ดที่ไม่มีรหัส และ credential ของ cloud ให้ใครก็ตามที่สั่ง Agent ได้
- **ทั้งเน็ตโดยไม่จำกัดการอ่าน แค่เตือน**: research จากไฟล์ในเครื่องผสมกับเว็บได้ทันที แต่หน้าเว็บไหนก็มีโอกาสดึงไฟล์ทั้งเครื่องออกไป

## Consequences

- Agent ติดต่อ Provider ได้เสมอโดยไม่ต้องอยู่ในรายชื่อ
- งาน research ที่แค่อ่านหรือค้นข้อมูล ใช้ web search กับ web fetch ของ Provider ได้โดยไม่ต้องเปิด Egress เพราะเซิร์ฟเวอร์ของ Provider เป็นคนเข้าเว็บ และ web fetch ของ Anthropic ดึงได้เฉพาะ URL ที่เคยปรากฏในบทสนทนา แต่ใช้ได้เฉพาะ Provider ที่มี tool นี้ Provider ที่ไม่มีให้ค้นผ่าน Connector และเปิดเว็บด้วย `web_fetch` ของเราที่อยู่ใต้ Egress (ADR 0040)
- proxy ต่อ Agent ต้อง spike บน sandbox-runtime ก่อนเริ่มทำ
- ข้อจำกัดเรื่องรายชื่อโดเมนที่ใช้ร่วมกันทั้ง Machine ใน ADR 0008 ใช้กับ v0.1 เท่านั้น
