# Project แทน Team และ Entry ส่งงานให้พนักงานได้ทุกตัวแต่ส่งได้ชั้นเดียว

Team ตาม ADR 0003 และ 0026 คือกลุ่ม Agent บน Machine เดียวที่มี Flow กับ Entry แต่งานจริงต้องการมากกว่านั้น คือ repo ที่หลาย Agent ทำงานร่วมกัน ห้องแชตที่จัดตามงาน และทำงานหลายเรื่องพร้อมกันได้ ถ้ามีทั้ง Team และ Project คนจะงงว่างานนี้ควรตั้งเป็นอะไร เราจึงให้ Project มาแทน Team Project คืองานหนึ่งเรื่องที่มี Agent หลายตัวเป็นพนักงาน อยู่บน Machine เดียวด้วยเหตุผลเดิมของ ADR 0026 มี Entry ตัวเดียว มี Library เป็น wiki (ADR 0046) และมี repo ได้ (ADR 0047) Team ยังไม่ได้เขียนโค้ด (#20) การเปลี่ยนจึงแก้แค่เอกสาร

Flow แบบวาดเส้นของ ADR 0003 ถูกตัดออก ระบบ multi-agent ที่ใช้กันจริง เช่น subagent ของ Claude Code และ orchestrator-worker เกือบทั้งหมดเป็นหัวหน้าหนึ่งตัวที่ส่งงานให้ใครก็ได้ ถ้าให้วาดเอง คนส่วนใหญ่ก็ลากจาก Entry ไปหาทุกตัว และวาดผังบนมือถือก็ยาก Entry จึงส่งงานให้พนักงานได้ทุกตัว ส่งได้ชั้นเดียว พนักงานส่งต่ออีกไม่ได้ พนักงานที่โดนหลอกจึงสั่ง Agent อื่นไม่ได้ ซึ่งเป็นสิ่งที่ Flow ตั้งใจกัน ใน Turn หนึ่ง Entry ส่งงานได้ไม่เกินเพดานของ Project ค่าเริ่มต้นคือ 5 ครั้ง บทความเรื่องระบบ research แบบ multi-agent ของ Anthropic บอกว่างานเปรียบเทียบใช้ subagent สองถึงสี่ตัว ส่วนสิบตัวขึ้นไปใช้กับงานที่ซับซ้อนจริงๆ ห้าครั้งจึงพอสำหรับงานทั่วไป เมื่อถึงเพดาน การส่งครั้งถัดไปได้ error กลับไปที่ Entry แต่ Turn ไม่จบ Entry ทำเองหรือสรุปผลต่อได้ ตัวกันเรื่องเงินจริงคือ Budget ของพนักงานแต่ละตัว (ADR 0043) เพดานนี้กันไม่ให้งานแตกเป็นหลายสิบกิ่งในทีเดียว คำแนะนำที่เคยอยู่บนเส้นย้ายไปอยู่ในคำอธิบายของพนักงาน เช่น "ใช้ตัวนี้เมื่อต้องรีวิวโค้ด" และ Entry เลือกเองว่าจะส่งให้ใคร ถ้าไม่อยากให้มีใครสั่ง Agent ตัวไหน ก็ไม่ต้องใส่ตัวนั้นเข้า Project ส่วนที่กันจริงยังเป็นการตรวจสิทธิ์ทุกครั้งที่ส่งงาน (ADR 0010) กับ Allowlist และ Approval ของพนักงาน Agent ตัวหนึ่งเป็น Entry ของ Project หนึ่งและเป็นพนักงานของอีก Project ได้ กฎของ ADR 0003 ที่ห้ามการส่งงานทั้งเครื่องรวมกันเป็นวงจึงยังอยู่

ห้องของ Project ในแอปก็คือ Task ของ Project ไม่มีแนวคิดห้องแยก Member พิมพ์ได้แค่ใน Task ของ Entry และหลายคนพิมพ์ใน Task เดียวกันได้ (ADR 0010) งานของพนักงานแสดงเป็นการ์ดในห้องที่อัปเดตสด เห็นสถานะและ Character ของแต่ละตัว กดขยายอ่านได้แต่พิมพ์ไม่ได้ เพราะถ้าแทรกคุยกับพนักงานตรงๆ Entry จะไม่รู้ว่าแผนเปลี่ยน ต้นไม้ของ Task ยังดูได้เหมือนเดิม

## Considered Options

- **คง Flow แบบวาดเส้นตาม ADR 0003**: คุมได้ละเอียด และรองรับงานที่ส่งต่อหลายทอด เช่น writer ไป editor ไป publisher แต่ทุก Project ต้องวาดผังก่อนใช้ และผังส่วนใหญ่ก็ออกมาเป็นรูปดาว เพิ่มเส้นระหว่างพนักงานทีหลังได้แบบ additive ถ้ามีคนต้องการจริง
- **Project เป็นชั้นที่ครอบหลาย Team**: แบ่งทีมย่อยในงานใหญ่ได้ แต่มีแนวคิดเพิ่มอีกชั้น และต้องตอบว่าส่งงานข้ามทีมใน Project เดียวกันได้ไหม
- **ให้พนักงานสั่งงานกันเองเหมือนคน**: เหมือนทีมจริงกว่า แต่ Agent ถือ Turn ไว้ระหว่างรอผล ถ้า A สั่ง B ขณะที่ B สั่ง A ทั้งคู่จะรอกันตลอด งานส่งกลับไปกลับมาได้ไม่จบ และพนักงานที่โดนหลอกจะสั่งตัวอื่นได้ ทางที่ได้ประโยชน์ใกล้กันคือให้พนักงานถามกันได้ด้วย Ask (ADR 0046)
- **ห้องเป็นช่องแบบ Slack ที่มีหลาย Task**: จัดกลุ่มงานได้อีกชั้น แต่ลำดับชั้นเพิ่มเป็น Project ห้อง Task และต้องตอบว่าสิทธิ์กับ worktree ผูกกับห้องหรือกับ Task ใช้ป้ายติด Task ได้ผลใกล้กัน
- **@ พนักงานแล้วคุยกับพนักงานตรงๆ ในห้อง**: เหมือนแชตกลุ่มของคน แต่ในห้องเดียวมีหลายบทสนทนาสลับกัน และไม่ชัดว่าใครคุมงาน

## Consequences

- ADR 0003 ถูกแทนด้วย ADR นี้ ส่วน ADR 0026 ยังใช้ได้โดยอ่าน Team เป็น Project
- ทุก Task ของ Project ผ่าน Entry ถ้า Agent ทำได้ทีละ Turn ห้องต่างๆ จะรอกันที่ Entry การทำงานขนานจึงต้องใช้ Worktree (ADR 0047)
- งานที่ต้องส่งต่อหลายทอดทำผ่าน Entry ทุกครั้ง ซึ่งใช้ token ของ Entry มากขึ้น
- คนที่มี Manage ที่ Project ปรับเพดานการส่งงานได้ งานที่ต้องแตกกว้างจริงๆ ต้องตั้งเพิ่มเอง
