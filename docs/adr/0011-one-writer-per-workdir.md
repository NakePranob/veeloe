# Workdir หนึ่งมีคนเขียนได้ทีละคน: Agent ทำทีละ Turn และ Subagent อ่านได้อย่างเดียว

ถ้ามีสองงานแก้ไฟล์ใน Workdir เดียวกันพร้อมกัน โค้ดของสองงานจะทับกัน เราจึงให้ Agent ทำได้ทีละ Turn Agent จะนับว่าไม่ว่างเฉพาะระหว่าง Turn รวมถึงตอนที่รอ Approval ส่วน Task ที่เปิดค้างไว้ไม่ได้ถือ Agent งานที่เข้ามาตอน Agent ไม่ว่าง ไม่ว่าจะเป็น Task ใหม่ ข้อความต่อใน Task เดิม หรือ Delegation จะต่อคิวอยู่ที่ Runtime ตามลำดับที่เข้ามา และผู้ส่งจะรู้ทันทีว่าอยู่คิวที่เท่าไหร่ Hub ยังคงไม่มีคิวตาม ADR 0005 ส่วน Subagent ที่ Agent สร้างขึ้นระหว่างทำ Task อ่านได้อย่างเดียว ถ้าอยากให้งานเดินขนานกัน ให้สร้าง Agent เพิ่มซึ่งมี Workdir ของตัวเอง และไม่เสียเงินเพิ่มเพราะเราคิดเงินตามจำนวน Machine

## Considered Options

- **หลาย Task พร้อมกัน โดยแยก git worktree ให้แต่ละ Task**: เร็วกว่า แต่ใช้ได้เฉพาะ Workdir ที่เป็น git และต้องมานั่ง merge ทีหลัง ส่วน Character ก็จะบอกได้ไม่ชัดว่าตอนนี้กำลังทำอะไร
- **ตอบกลับว่าไม่ว่างแทนการต่อคิว**: ง่ายกว่า แต่สั่งงานล่วงหน้าไม่ได้ และ Agent ที่ส่ง Delegation มาต้องคอยลองใหม่เอง
- **ให้ Task ถือ Agent ไว้จนกว่าจะปิด Task**: งานใน Task เดียวกันจะต่อเนื่องแน่นอน แต่ต้องคอยกดปิด Task ทุกครั้ง และคิวจะติดง่าย

## Consequences

- Task ที่ทำต่อเนื่องกันใช้ Workdir เดียวกัน ไฟล์ที่ Task ก่อนหน้าแก้ไว้จึงอยู่ให้ Task ถัดไปเห็นด้วย
- Approval ที่รออยู่จะถือ Agent ไว้ได้นานที่สุดเท่ากับเวลาหมดอายุ (ค่าเริ่มต้น 1 ชั่วโมง) หลังจากนั้นจะนับว่าถูกปฏิเสธ แล้วคิวก็เดินต่อ
- ถ้า Machine ดับ งานที่ต่อคิวอยู่จะค้างอยู่บนเครื่องนั้นจนกว่าเครื่องจะกลับมา
- งานจาก Channel ต่อคิวเดียวกัน แต่ Member ตั้งเพดานจำนวนงานที่รอได้ต่อ Channel เพราะคนในแชตไม่ใช่ Member และค่า token เป็นของ Member ที่ผูก (ADR 0028)
- Agent ที่ส่ง Delegation ถือ Turn ไว้จนได้ผลกลับครบ (ADR 0003) ระหว่างนั้นถือว่าไม่ว่าง งานที่ส่งมาหาตัวนั้นจึงต่อคิว
- Subagent เขียนไฟล์ไม่ได้เลยนอกจาก TMPDIR ของตัวเอง จึงรันคำสั่งที่เขียนไฟล์ไม่ได้ เช่น `npm test` หรือ build ที่สร้าง cache Agent แม่ต้องรันเอง Subagent มีไว้แตกงานอ่านและคิดให้ขนานกัน ส่วนงานแก้ไฟล์ที่ต้องขนานกันให้ใช้ Agent อีกตัวใน Team ซึ่ง Member เห็นเป็นกิ่งในต้นไม้ของ Task และกด Stop ได้
