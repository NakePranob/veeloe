# Invitation แนบ Grant ได้ คนที่มี Manage ออกได้ และ Turn ของคนที่ไม่มี Manage อ่านได้แค่ Workdir กับ Library

การให้คนใหม่ใช้ Agent ต้องรอ Owner ออก Invitation แล้วแจก Grant แยกอีกครั้ง ซึ่งช้า เราเคยคิดถึงลิงก์แชร์ใช้ได้หลายครั้ง แต่ลิงก์แบบนั้นไม่มีการเทียบรหัสกันกุญแจถูกสลับ (ADR 0031) และไม่มีคนรับรองกุญแจใหม่ ซึ่งขัดกับ ADR 0006 และ 0013 ปัญหานี้แก้ได้โดยไม่ต้องเพิ่มแนวคิดใหม่ (เจ้าของตัดสิน 2026-11-01): Owner หรือ Member ที่มี Manage ที่ Agent อย่างน้อยหนึ่งตัวออก Invitation ได้ และแนบ Grant ได้เฉพาะ Agent ที่ตัวเองมี Manage ลิงก์ยังใช้ได้ครั้งเดียว หมดอายุใน 24 ชั่วโมง และคนออกเทียบรหัสสั้นก่อนเซ็นรับรองเหมือนเดิม Hub ไม่รู้ Grant (ADR 0034) จึงตรวจไม่ได้ว่าคนเซ็นมี Manage จริงหรือไม่ ถ้าเชื่อลายเซ็นของ Member ทุกคน คนที่มีแค่ Use จะเซ็นเพิ่มคนเข้า Workspace ได้ ใบรับรองที่ Manager เซ็นจึงส่งผ่าน Runtime ของ Agent ที่แนบ Grant ซึ่งตรวจ Manage แล้วค่อยแจ้ง Hub แบบเดียวกับที่ Runtime อัปเดตโปรไฟล์ของ Agent (ADR 0006) ส่วนใบรับรองที่ Owner เซ็นส่งตรงได้เหมือนเดิม

คนที่เข้ามาเป็น Member เหมือนการเข้าองค์กร และอยู่จนกว่าจะมีคนเอาออก ไม่มีวันหมดอายุ คนที่มี Manage ถอน Grant ได้ (ADR 0010) ส่วนการลบ Member ยังเป็นของ Owner หน้ารายชื่อ Member แสดงว่าใครเป็นคนเชิญและใช้งานล่าสุดเมื่อไร

เมื่อคนที่ไม่ใช่เจ้าของเครื่องเชิญคนใหม่ได้ สิทธิ์ที่มากับ Use จึงต้องแคบลง เดิมทีเมื่อคุยกับ Agent ตรงๆ Agent อ่านได้ทุกไฟล์ที่ไม่ใช่ไฟล์ลับ (ADR 0008) ใครมี Use จึงขอไฟล์บนเครื่องของเจ้าของได้ นอก Project ขอบเขตการอ่านจึงตามคนที่ส่งข้อความของ Turn คนที่มี Manage อ่านได้ตามเดิม ส่วนคนที่มีแค่ Use หรือ Approve อ่านได้แค่ Workdir กับ Library sandbox เป็นตัวบังคับ และ supervisor เปิด worker ใหม่เมื่อ Turn ถัดไปต้องใช้สิทธิ์ต่างจากเดิมตามกลไกของ ADR 0026

ทุกคนที่ใช้ Agent ใช้ key ของ Provider ที่ตั้งบน Machine (ADR 0042) และ Budget ก้อนเดียวกัน (ADR 0043) ไม่มีเพดานต่อคน แอปแสดงว่าแต่ละ Member ใช้ไปเท่าไหร่ต่อเดือน แล้วแบ่งค่าใช้จ่ายกันนอกระบบ

## Considered Options

- **ลิงก์ใช้ได้หลายครั้งแบบแชร์ลงกลุ่ม**: กระจายได้ทีเดียว แต่เสียการเทียบรหัสและคนรับรองกุญแจ ถ้าอยากให้คนนอกมาลองควรใช้ Channel ซึ่งมีคนนอก, sandbox ที่จำกัด และ Budget เป็นเพดานอยู่แล้ว (ADR 0028)
- **ตัวตนใหม่แบบ Guest**: เห็นเฉพาะ Agent ที่ได้รับ แต่ ADR ทุกฉบับที่พูดถึง Member ต้องเพิ่มกรณีนี้ ซึ่ง ADR 0028 เคยปฏิเสธด้วยเหตุผลเดียวกัน
- **Grant มีวันหมดอายุ**: ลดสิทธิ์ที่ค้างจากการลืม แต่ไม่จำเป็นเมื่อการเชิญคือการรับเข้าองค์กร เพิ่มทีหลังแบบ additive ได้
- **ขอบเขตการอ่านตามค่าของ Agent**: คุยด้วยตัวไหนก็ได้ผลเหมือนกัน แต่ Owner เสียการอ่านกว้างใน Agent ตัวเอง และถ้าลืมตั้งก็ยังรั่ว
- **เพดาน token ต่อคน**: คนเดียวทำให้ทุกคนหยุดไม่ได้ แต่ต้องคอยตั้งตัวเลขเพิ่ม เจ้าของเลือกให้ตกลงกันนอกระบบ
- **หน้า Agent ที่แชร์กับฉัน**: ใน Workspace เดียวก็คือรายการ Agent ที่กรองตาม Grant และรวมข้าม Workspace ไม่ได้ เพราะกุญแจกับฐานข้อมูลแยกกัน (ADR 0031)

## Consequences

- Workdir ยังใช้ร่วมกัน ถ้า Kai ให้ Agent คัดลอกไฟล์เข้า Workdir คนที่มี Use ก็ขอดูได้
- เพื่อนร่วมทีมที่มีแค่ Use สั่งให้อ่าน repo นอก Workdir ไม่ได้ ต้องย้ายเข้า Workdir หรือใช้ Project
- คนที่มี Use ยังใช้ Connector ของ Agent ได้ (ADR 0039)
- คนที่ถูกเชิญเห็นชื่อ Agent และชื่อ Member ใน Workspace (ADR 0034, 0053)
- คนเดียวใช้ Budget หมดแล้วทุกคนหยุด จนกว่าคนที่มี Manage จะเพิ่ม
- E2E ต้องเสร็จก่อนเปิดให้คนอื่นใช้ (ADR 0005)
- ถ้า Machine ของ Agent ที่แนบ Grant ปิดอยู่ Manager จะรับคนเข้าไม่ได้จนกว่าเครื่องจะกลับมา ถ้าแนบ Grant หลาย Machine คนนั้นเข้า Workspace เมื่อ Runtime เครื่องแรกตรวจผ่าน และ Grant ของเครื่องอื่นมีผลเมื่อเครื่องนั้นออนไลน์
