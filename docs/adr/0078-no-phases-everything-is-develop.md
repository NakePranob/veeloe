# ไม่แบ่งงานเป็น phase งานทุกชิ้นอยู่บน develop

Status: accepted

เปลี่ยน ADR 0048 และ 0076: เดิมงานแบ่งเป็น phase ตามเลขรุ่น (v0.1 ถึง v0.6) และแต่ละ phase บอกว่าต้องมีอะไรบ้าง ตอนนี้ v0.1 ออกแล้ว ต่อจากนี้ไม่มี phase อีก งานทุกชิ้นเป็นงานบน `develop` เลือกทำตามความสำคัญตอนนั้น และเลขรุ่นเป็นแค่ป้ายตอนออก release

การแบ่ง phase ช่วยให้ v0.1 มีขอบเขตและจบได้ แต่พอใช้ต่อ มันทำให้ทุกการตัดสินใจต้องถามก่อนว่า "อยู่ phase ไหน" ADR หลายฉบับต้องผูกกับเลขรุ่น และเมื่อย้ายของข้าม phase (เช่น push ใน ADR 0076) ต้องแก้ตามหลายที่ ส่วนเรื่องที่ phase ปกป้องจริงๆ คือเงื่อนไขด้านความปลอดภัยก่อนให้คนอื่นใช้ ซึ่งเขียนเป็นเงื่อนไขตรงๆ ได้โดยไม่ต้องมีเลขรุ่น

**การตัดสินใจ:**

- งานทุกชิ้นอยู่บน `develop` และ commit ตรงเข้า `develop` (AGENTS.md) ไม่มีแผนว่าอะไรอยู่รุ่นไหน
- เลขรุ่น (v0.2, v0.3, …) เป็นแค่ tag ตอนออก release ของ Runtime, image ของ Hub และ build ของ Controller
- **เงื่อนไขก่อนให้คนอื่นนอกจาก Owner ใช้** ยังอยู่ครบ และห้ามข้าม:
  - E2E เพราะ Hub ยังอ่านเนื้อหาระหว่างส่งต่อได้ (ADR 0005, 0063)
  - ตัวอัปเดตที่ตรวจลายเซ็นของ release (ADR 0009)
  - ตรวจ Runtime บน Linux จริง (#51)
- push ยังมาทีหลังฟีเจอร์อื่นตามเหตุผลใน ADR 0076 แค่ไม่เรียกว่า v0.6

**ADR เก่าที่เขียนถึงเลขรุ่น อ่านแบบนี้:**

| ในADR เก่า | หมายถึง |
|---|---|
| v0.1 | รุ่นแรกที่ออกแล้ว (v0.1.0) ใช้บอกว่าตอนนั้นมีหรือไม่มีอะไร |
| v0.2, v0.4, v0.5 | งานที่มาทีหลัง ไม่มีลำดับบังคับ |
| v0.3 | ก่อนให้คนอื่นนอกจาก Owner ใช้ หรือเมื่อมี Member คนที่สอง |
| v0.6 | push ซึ่งมาหลังฟีเจอร์อื่น (ADR 0076) |

## Considered Options

- **แบ่ง phase ต่อจาก v0.2**: มีแผนให้เห็นยาว แต่ต้องแก้ ADR ทุกครั้งที่ลำดับเปลี่ยน และงานเล็กต้องรอ phase ของมัน
- **แก้ ADR เก่าทุกฉบับให้เลิกพูดถึงเลขรุ่น**: อ่านง่ายกว่าในระยะยาว แต่เขียนประวัติการตัดสินใจใหม่ และ diff ใหญ่โดยไม่ได้อะไรเพิ่ม ตารางด้านบนพอแล้ว

## Consequences

- ไม่มี milestone ตามรุ่นบน GitHub issue บอกงานถัดไปโดยไม่ผูกกับรุ่น
- คนที่อ่าน ADR เก่าต้องแปลเลขรุ่นด้วยตารางนี้
- ก่อนเปิดให้คนอื่นใช้ ต้องไล่เงื่อนไขในข้อ "ก่อนให้คนอื่นนอกจาก Owner ใช้" ให้ครบเอง เพราะไม่มี phase ที่บังคับให้ทำ
