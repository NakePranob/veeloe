# Allowlist เป็นคำนำหน้าของคำสั่ง bash และมีไว้กันความผิดพลาด ไม่ใช่กำแพงความปลอดภัย

Approval เกิดได้กรณีเดียวคือ Agent จะทำสิ่งที่ไม่อยู่ใน Allowlist (ADR 0003) แต่ยังไม่มีที่ไหนบอกว่ารายการใน Allowlist หน้าตาเป็นยังไง Allowlist คุมแค่คำสั่ง bash รายการแต่ละตัวคือคำนำหน้าของคำสั่ง เทียบทีละคำจากต้นคำสั่ง เช่น `npm test` ครอบ `npm test -- --watch` คำสั่งที่ต่อกันหลายท่อนด้วย `&&`, `;` หรือ `|` ต้องผ่านทุกท่อน และสิ่งที่แยกท่อนให้แน่ใจไม่ได้ เช่น `$(...)`, backtick หรือ `eval` ต้องขอ Approval ทุกครั้ง ส่วน tool ที่ทำกับไฟล์ ได้แก่ read, write, edit, glob และ grep ไม่ผ่าน Allowlist เพราะ sandbox คุมอยู่แล้วว่าเขียนได้แค่ใน Workdir และอ่านได้แค่ไหน (ADR 0008) ถ้าการแก้ไฟล์ทุกครั้งต้องขออนุมัติ มือถือจะเด้งทุก Task จนคนกดอนุมัติโดยไม่อ่าน

ทุกรายการมาจาก Member ที่มี Manage เซ็นเพิ่ม (ADR 0006, 0010) ไม่มีคำสั่งที่ผ่านเสมอโดยไม่อยู่ในรายการ Agent ที่สร้างใหม่เริ่มจาก Allowlist ว่าง แต่หน้าสร้าง Agent ติ๊กชุดคำสั่งอ่านอย่างเดียวไว้ให้ ได้แก่ `ls`, `pwd`, `cat`, `head`, `tail`, `wc`, `git status`, `git diff` และ `git log` Member เอาออกได้ก่อนเซ็น ชุดนี้ไม่มี `find` เพราะมี `-exec` กับ `-delete` ไม่มี `sed` เพราะมี `-i` และไม่มี `git` หรือ `npm` ทั้งตัว Approval มีปุ่มอนุญาตตลอดให้เฉพาะ Member ที่มี Manage ปุ่มนี้คือการอนุมัติพร้อมกับแก้ Allowlist ซึ่งเซ็นทั้งคู่ แอปเสนอคำสั่งเต็มบรรทัดเป็นรายการใหม่ Member ตัดท้ายออกให้เหลือคำนำหน้าที่ต้องการได้ และแอปต้องบอกว่ารายการนั้นครอบคำสั่งไหนบ้าง ถ้าคำสั่งมีหลายท่อน แอปเสนอเฉพาะท่อนที่ยังไม่อยู่ในรายการ ส่วน Member ที่มีแค่ Approve อนุมัติได้ครั้งเดียวหรือปฏิเสธ

Allowlist ไม่ใช่กำแพง เพราะแก้ไฟล์ได้โดยไม่ต้องขอ Agent ที่โดนหลอกจึงเลี่ยงได้ เช่น แก้ script test ใน `package.json` แล้วรัน `npm test` ที่อยู่ในรายการ หรือตั้ง `core.fsmonitor` หรือ `diff.external` ใน `.git/config` แล้วรัน `git status` หรือ `git diff` ADR 0008 ก็บอกไว้ตั้งแต่แรกว่า Allowlist มองไม่เห็นว่าข้างในคำสั่งทำอะไร หน้าที่ของ Allowlist คือให้ Agent ต้องหยุดถามก่อนทำอะไรเกินที่ตั้งใจ ส่วนกำแพงจริงคือ sandbox กับ Egress (ADR 0008, 0029) Agent ที่คนนอกสั่งได้จึงพึ่งการอ่านได้แค่ Workdir ของตัวเองกับ Egress ของตัวเอง ไม่ได้พึ่ง Allowlist (ADR 0028)

## Considered Options

- **คุมทุก tool รวม write และ edit**: ปลอดภัยกว่านิดเดียว เพราะ sandbox กันการเขียนนอก Workdir อยู่แล้ว และ Workdir ที่เป็น git กู้คืนได้ แต่ Approval จะเด้งตลอด
- **เปิดหรือปิด tool ทั้งตัว**: หยาบเกินไป เปิด bash ทั้งตัวเท่ากับทำได้ทุกอย่างที่ sandbox ปล่อย
- **ต้องตรงกับคำสั่งทุกตัวอักษร**: แคบเกินไป เติม flag ตัวเดียวก็ต้องขอใหม่
- **ไม่มีปุ่มอนุญาตตลอด ให้แก้ Allowlist แยกในหน้าตั้งค่า**: การแก้ Allowlist ต้องตั้งใจทำ แต่ Approval ที่เด้งซ้ำทำให้คนกดอนุมัติโดยไม่อ่าน ซึ่งแย่กว่า Allowlist ที่ตั้งไว้ดี
- **เริ่มจาก Allowlist ว่างโดยไม่เสนออะไร**: ไม่มีอะไรที่ Member ไม่ได้เลือกเอง แต่ Task แรกๆ จะขอ Approval แม้แต่ตอน `ls`

## Consequences

- รายการ `git push` ครอบ `git push --force origin main` ด้วย คนตั้งต้องตั้งให้แคบเท่าที่ตั้งใจ
- กฎการแยกท่อนของคำสั่งเป็นโค้ดด้านความปลอดภัย ต้องเขียนเป็น spec และมี test ที่ครอบทุกแบบที่ต้องขอ Approval
- tool ชนิดอื่นที่จะมีทีหลัง เช่น tool จาก MCP จะเพิ่มรายการชนิดใหม่เข้า Allowlist แบบ additive (ADR 0023)
